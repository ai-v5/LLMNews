**801 最值得学的不是“AI 能自己训练出更强的 AI”，而是：大训练不能重来，小实验却可以反复做。** 团队让智能体帮忙查故障、改数据、做短实验，再由人决定什么值得带进主训练。上一轮试错的证据会留给下一轮。这就是论文所说的 RSI 式闭环，也是它和“模型自主升级”之间最重要的区别。

SII 与 Xinxu AI 报告称，他们沿用 Qwen3-30B-A3B 架构，从随机初始化训练了自己的 801-30B-A3B：总参数 30B，每个 token 激活约 3B，主跑约三个月，处理了 11.8T tokens，不等于 11.8T 不重复数据。主跑前还有两次分别在 1T 和 3T 停止的试跑。“不能重来”指完整主跑不是廉价、可重复的实验，不是说团队只按下过一次启动键。[技术报告 §1–2](https://arxiv.org/html/2611.10719v1)

## 一、六条闭环，究竟在改什么？

一个最小闭环是：**发现问题 → 提出改动 → 小范围验证 → 保留证据 → 决定下一步。** 801 没有用一个总榜分数驱动所有改动，而是给不同环节选了不同的反馈。可以把表里的最后一列理解成“为什么下一轮不必从头猜”。

| 闭环 | 看到什么信号 | 验证后留下什么 |
| --- | --- | --- |
| 基础设施调试 | loss、梯度或 MoE 专家负载异常 | 可复查的日志、配置差异、可复跑的诊断和修复记录 |
| 数据调试 | 输出模板突变、重复或多样性不足 | 问题样本、可疑数据来源、过滤或修订规则 |
| 训练配方 | 基座分数停滞、不同 checkpoint 排名不稳 | 小规模 SFT、学习曲线和不同评测协议下的结果 |
| 分类器开发 | 标签规则对边界样本判错 | 误判样本、修订后的规则和再次评测的结果 |
| 站点发现 | 某个领域的高质量来源不足 | 核验过的候选站点，以及接受或排除的理由 |
| 爬虫覆盖 | 已知好站点却没有抓到足够的有效内容 | 覆盖缺口、抓取策略的改动和复查结果 |

前三个闭环把异常或分数变成可执行的诊断；后三个把原先靠经验做的工作变成可检查的结果。它们共享上下文：配置对应哪个 checkpoint，试过什么，失败是因为改动本身不好，还是因为实验没跑成。**递归主要发生在流程和组织记忆里，不是在 801 的权重里。** 公开报告没有证明 801 自己修改了训练系统，也没有测量这一代模型是否让下一代模型更善于改进训练。[报告 Figure 2、§3–5](https://arxiv.org/html/2611.10719v1)

## 二、系统工程上最扎实的一例：用注意力成本，而不是 token 数给 DP 分工

把几份文档装进同样大小的 256K pack，不代表这些 pack 的计算量相等。若文档之间用独立的注意力边界，在其他条件相同的近似下，attention 工作量更接近各段长度平方之和。举个只算这一项的例子：一段 256K 与四段 64K 的总 token 数相同，前者的平方和却是后者的四倍。这个四倍不是整个 step 的耗时差；MLP、通信和实际内核效率还要另算。

同步训练会等慢的一组。如果只按 token 数做 packing，某个 DP 副本分到更贵的 pack，其他副本也可能跟着等。作者在有限窗口内调整 pack 的分配，让各个 DP 副本的估算成本更均匀。在 **256 GPU、CP=4、DP=64** 的对照中，一个 DP 副本每个 microbatch 处理一个 pack，排序窗口为八个全局 microbatch；作者报告吞吐 **1,126 → 2,543 TGS，约 2.26 倍**。这是 256K、这套并行和数据条件下的数据加载对照，**不是整个 11.8T 训练快了 2.26 倍**。

窗口也不是越大越好。文档长度可能和领域、难度相关，按长度大范围重排会改变每一步看到的数据组合。作者报告平滑后的 loss 轨迹相近，最终基准差异在运行波动内；这不是对任意数据集或窗口的等价性保证。迁移到另一条训练线时，值得一起看的是 **最慢 DP 副本耗时、整体吞吐、样本顺序和数据域占比**，而不是只抄一个窗口大小。[报告 §7.1、Figures 22–23](https://arxiv.org/html/2611.10719v1#S7.SS1)

优化器实验也有一个比总榜更有用的对照：在试跑中、保持全局负载均衡和配置的数据混合不变，约 604B tokens 时，全 AdamW 为 45.60，专家矩阵用 Muon 为 47.89，专家和注意力矩阵都用 Muon 为 48.28。同一组里的局部负载均衡拿到 48.52，但团队最后选择了他们认为内部训练更稳的全局负载均衡。这个结果可以指导下一次实验，不足以证明某个配置在其他模型或随机种子下必胜。[报告 §7.2、Table 5](https://arxiv.org/html/2611.10719v1#S7.SS2)

## 三、基座分数不涨，模型可能还在变好

预训练指标回答“这份 checkpoint 现在会什么”。团队还想知道“给它相同的少量后训练，它能学到什么”。这两件事不总是同一个排序。

Figure 11 有一个直观例子：同一组 checkpoint 中，**159k 从基座第 1 变成 Tiny-SFT 后第 3；210k 从第 6 变成第 1**。这不是两者差异有统计显著性的证明，但它说明如果只看基座榜，可能选错值得做下一轮实验的 checkpoint。

作者用了三把尺子：

1. **Tiny-SFT**：用固定的一套轻量监督微调探针，看看基座能否更容易适应。论文使用 6.33B tokens，不含 RL；“Tiny”是相对完整后训练，不是说它没有成本。
2. **学习曲线**：别只看第一步分数，也看给更多 SFT 预算时涨得多快。比如 BFCL 上，801 早期落后 Qwen3-30B-A3B，随后在这套训练和评测协议下反超。更陡的曲线不保证换任务或继续外推后仍如此。
3. **多协议评测**：换几种评测方式，减少单个提示模板或输出格式造成的误判。取最高值只是“这些协议里测到的最好结果”，不是模型的能力上限。

这套方法适合做 checkpoint 筛选，不应替代独立验证。若相邻分数差很小，先复查相同配置下能否重复；如果用同一套题和提示反复挑配方，最好另留一批最后才使用的评测。[报告 §4、§8.4](https://arxiv.org/html/2611.10719v1#S4)

## 四、智能体还在生产预训练数据，但要分清产量和实际用量

论文描述了这样一条生产链：约 **26 万个原始 PR → 22 万个可执行任务 → 约 200 万条候选轨迹 → 约 110 万条通过验证的轨迹，超过 100B tokens**。项目在九种智能体框架上生成轨迹，加入其他来源后，报告的数据池总量为 134B tokens。这个数字不等于喂给模型的 134B，也不等于 134B 份相互独立的有效监督。按论文的阶段配比，最后 256K 阶段是 200B tokens，其中智能体类占 15%，按配比约为 30B tokens；这是阶段口径，不是整个主跑的实测摄入量。

真正难的是让任务说明、运行环境和验证互相一致，以及区分“跑过测试”和“解决了正确的问题”。对训练团队来说，**数据漏斗比产量更值得跟踪**：各类任务过了哪道门、被拒的原因是什么、重复轨迹有多少、改配比后哪个未见任务真的更好。论文没有给出足以把最终榜单提升单独归因于这批轨迹的消融。[报告 §6–7](https://arxiv.org/html/2611.10719v1#S6)

## 五、“超过 Qwen”到底在哪些条件下成立？

| 对比口径 | 801 的结果 | 该怎么解读 |
| --- | --- | --- |
| 同进度的三版预训练，22 项均分 | 1T 时 **47.78 → 51.96 → 56.83** | 相同 token 进度下，后续版本更好。数据、配置和修复一起变了，不是 RSI 或任何单项修复的净收益，也不代表 GPU 小时相同。 |
| 基座对基座，13 项均分 | **73.13**；Qwen3-30B-A3B 为 **66.16**，Qwen3.5-35B-A3B 为 **76.67** | 在报告这组基座评测上超过 Qwen3-30B，没超过 Qwen3.5-35B。 |
| 同一份 Tiny-SFT 数据，通用 13 项 / 专项 5 项 | 通用 **81.34 vs 83.76**；专项 **28.70 vs 20.54**，对照为 Qwen3.5-35B-A3B | 一边落后，一边领先。SimpleQA Verified 一项贡献了专项均分差距的约 55%；除去该项，剩余四项均分仍领先。报告对 SimpleQA 做了 8-gram 去重检查，不等于排除所有污染途径。 |
| 801 轻量 SFT vs 厂商发布的后训练模型，智能体 4 项 | 四项均分 **58.43**，表内第一；KernelBench **77.60** | 不是同后训练配方。801 只在 KernelBench 单项第一；例如 SWE-bench Verified 为 **68.95**，低于 Qwen3.6-35B-A3B 的 **71.65**。按表重算，去掉 KernelBench 后 801 为 **52.05**，Flint 为 **53.24**。 |

所以最稳妥的说法是：**801 在特定基座对照和部分适应任务上表现强，尤其是 KernelBench；没有证据说它整体超过 Qwen，更没有证据说领先分数由 RSI 单独带来。** 如果要回答 RSI 的贡献，需要至少比较同预算、同起点下的人类单独调优和人机闭环，并同时记录 GPU 小时、人工投入、从异常到定位的时间和最终留出集分数。[报告 Tables 7–9](https://arxiv.org/html/2611.10719v1#S8)

## 六、代码核查：能看哪些，不能复现哪些？

截至 2026 年 11 月 15 日，本次核查的 [801 官方仓库](https://github.com/GAIR-NLP/801-30B#release) 有报告、图表和 README；尽管论文写了发布计划，README 仍标注 Base 权重尚待发布。官方链接指向 [Tiny-SFT 数据集卡](https://huggingface.co/datasets/SII-GAIR-NLP/801-30B-A3B-tiny-sft-dataset)，但数据访问受限，本次未下载。仓库中未找到可运行的 801 生产训练器、六条闭环的编排代码，或报告评测的完整脚本。**公开方法和公开可复现训练系统，是两件事。**

可以读到具体实现的是另一个项目 [DataEvolve](https://github.com/GAIR-NLP/DataEvolve)。801 报告说分类器等环节受它启发。在 DataEvolve 的 [pipeline.py](https://github.com/GAIR-NLP/DataEvolve/blob/1593baeea18c7f3459e46fbb2602ae8d1d50137b/pipeline.py) 里，代码先观察样本，再用历史记录设计新的清洗提示，抽样清洗，调用评审模型给出分数和诊断，最后把结果写回记录，供下一轮挑选父策略。代码展示了怎样把经验持久化；评审模型给出的分数却不是天然的客观真值。它也不是 801 生产线的源码，本次只检查了代码，没有执行或复现实验。[报告 §5.1](https://arxiv.org/html/2611.10719v1#S5.SS1)

## 七、这是不是第一次？最值得借鉴的是什么？

“第一次”要保留作者的限定：**据作者所知，这是首个详细记录 RSI 式闭环贯穿一次完整前沿预训练的公开案例。** 更宽的说法站不住。2026 年 8 月，Hugging Face 已用智能体搜索 2B 视觉语言模型的预训练数据配比，作者口径的最佳混合把组合指标从 58.8% 提到 62.8%，但那是单一环节且搜索可以反复训练。LinkedIn 10 月提交的报告也披露了生产机器学习闭环，独立的 AutoResearch 队列中有 28/100 个管线在最终留出集超过原始基线，但任务是排序、内容理解和推荐，不是前沿语言模型从零预训练。这些先例说明闭环不是新东西；801 的价值在于把多个闭环接到同一条难以重跑的预训练线上。[Hugging Face 原文](https://huggingfacem4-vlm-data-autoresearch.hf.space/)，[LinkedIn 原文](https://arxiv.org/html/2611.00384v1)

如果只从 801 带走一件事，我会先做**可重放的实验记录**：每次告警绑定到 checkpoint、代码、配置和数据版本；用便宜的重放去检验一个明确假设；把结果、失败原因和上线条件留给下一轮。先证明这个流程在同等预算下能更快定位问题，再谈让它接管更多决策。801 给出了值得借鉴的训练组织方式，但没有把这个问题的最后一道证据补齐。
