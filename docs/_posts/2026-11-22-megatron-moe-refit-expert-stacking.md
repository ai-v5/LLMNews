> 公开资料筛选截至北京时间 11 月 22 日 05:37，向前 24 小时。

**搬同样多的权重，把许多独立的小传输改成一个分布式张量操作，就能缩短 MoE refit。** Megatron 的公开对照中，Nemotron-3-Ultra 在单个 GB200 NVL72 柜里的重分片从 1,602 ms 降到 706 ms；跨两个柜的另一种部署从 35,891 ms 降到 22,615 ms。最能解释原因的却是一个小实验：不增加、不减少逻辑权重字节，只改变专家张量的拆分粒度，旧路径的时间就从 950 ms 变到 322 ms。

本文讨论的是**权重怎么从训练 GPU 搬到推理 GPU**，不是版本切换如何对正在生成的请求生效。[Megatron-LM #8606](https://github.com/NVIDIA/Megatron-LM/pull/8606) 于 11 月 21 日 00:27:25 UTC（北京时间 08:27）合入。性能数字是 PR 作者在明确记载的早期分支提交上采得，不是本文复测，也不是在最终合入提交上重跑。

## 一、EP 重分片的对象不是一个专家，而是一组同类投影

强化学习采用不共卡的训练与推理池时，训练 rank 和推理副本可以有不同的专家并行（EP）布局。一次 refit 要把新权重按推理端所需的归属重分片。这里的 M2N 是从一组训练 rank 向一组推理 rank 重新分配张量，不是 MoE 前向的 token dispatch/combine。

旧的 native M2N 计划把每个专家权重写成一个单源 rank、单目标 rank 的操作。即使一柜有许多链路，这个工作单元只描述其中一对 rank 之间的搬运。新计划找到同层同类投影的一整组专家，把它描述成逻辑形状 `[E, *expert_shape]` 的张量，沿专家轴在源、目的 EP 组分片。一个合格投影组对一个目的 EP 组只需一个 spec。多个目的 EP 组还可以按轮转使用不同的来源 EP 副本。由 [planner diff](https://github.com/NVIDIA/Megatron-LM/pull/8606/files) 可核到这些约束。

```text
逐专家：专家 0 → rank a；专家 1 → rank a；专家 2 → rank b；……
按投影组：训练 EP [各 rank 的一段专家] → M2N → 推理 EP [新的一段归属]
```

**组得起来，不等于每次都零拷贝。** 已经背靠背存在同一块 storage 的兼容参数可以直接做 view；不满足物理连续条件时，源端可能要打包，目的端也可能要经暂存后批量写回。接收端有转换（如 Torch MXFP8）时，仍可先接入暂存，再逐专家完成转换。缺专家、投影形状或 dtype 不一致、源和目的 EP 组重叠、专家自身还做 ETP 分片，以及 packed/strided 的某些专家布局，都可能使该投影组回到逐专家路径。PR 另行增加 dense SwiGLU 的 strided TP shard 描述能力，**不等于所有 strided 专家都能堆叠**。[实现与测试](https://github.com/NVIDIA/Megatron-LM/pull/8606/files)。

## 二、最干净的证据：字节不变，粒度变了

作者在 Qwen3-30B 的诊断实验中，将等量权重拆为 128 或 16 个专家。测得：

| 等逻辑字节的拆分 | 逐专家 M2N | 堆叠 M2N |
| --- | ---: | ---: |
| 128 个专家 | 950 ms | 146 ms |
| 16 个专家 | 322 ms | 144 ms |

这是用来定位 refit 开销的**传输诊断**，不是说实际部署把模型改成 16 个专家后，推理质量不变。其价值在于区分“需要传更多数据”与“同样的数据被切得过碎”。

再看作者的计时：主机在原生调用内消耗的时间只有 19–68 ms，解释不了数百毫秒的差异。作者将主要代价归因于逐专家搬运时只有少数链路工作、其余 EP 互联闲置。这是**有对照支持的机制解释**，PR 没有给出逐链路计数器来量化每条链路的占用。换一个拓扑、不同的消息并行度或 EP 布局，瓶颈可以迁移。[PR 的定位实验](https://github.com/NVIDIA/Megatron-LM/pull/8606)。

## 三、GB200：柜内和跨柜都获益，但不能用三行算出“跨柜惩罚”

以下是 Nemotron-3-Ultra 的 BF16 作者测量。训练和推理使用不同 GPU；每行中三种后端在同一作业内比较，预热 3 次后取 10 次中位数。两列 M2N 都已启用 split communicator；逐专家列是同一分支关闭堆叠。数据来自 `cc5989a57`，PR 明确没有在后续复核时重跑大表。

| 作业规模与放置 | 训练 → 推理 EP（均 TP8） | 逻辑字节/次 | NCCL send/recv | 逐专家 M2N | 堆叠 M2N | 逐专家 ÷ 堆叠 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 8 节点，一柜 | EP16 → EP8 × 2 副本 | 2,248 GB | 4,597 ms | 1,602 ms | 706 ms | 2.27× |
| 16 节点，一柜 | EP32 → EP8 × 4 副本 | 4.50 TB | 3,410 ms | 3,210 ms | 1,302 ms | 2.47× |
| 32 节点，两柜 | EP64 → EP8 × 8 副本 | 8.99 TB | 32,042 ms | 35,891 ms | 22,615 ms | 1.59× |

读表时有四点：

1. **6.51× 是 8 节点堆叠 M2N 对 send/recv，不是对旧 M2N。** 同一行若要估计堆叠本身的收益，应使用 2.27×。
2. **32 节点是训练独占一柜、推理独占另一柜。** 作者说明该放置的数据都要跨柜走 InfiniBand。在这一行，旧 M2N 比 send/recv 慢，堆叠后反而快约 1.42×。但 16→32 节点同时改变训练 EP、目的副本数和字节数，不能把各行耗时之差全部归给跨柜。
3. **默认通信器设置也是代码变化，但不是这张表的解释。** 两列 M2N 都启用了 split；另有 Ultra 的首轮 refit 12.6→8.9 s，作者同时报告通信器数 34→4。这是冷启动开销，不应与预热后表格混加。
4. **逻辑字节除以耗时得到交付速率，不是单链路带宽。** 例如 2,248 GB / 0.706 s ≈ 3.18 TB/s，是按这一行逻辑交付量计算的作业级速率。无 rank 到 NIC 的映射、链路方向、路径及流量计数器，不能直接写成“每卡”或“每条链路”带宽，更不能把 TB/s 与双向峰值随意相除求利用率。

同一 PR 在 8 节点还报告 Qwen3-235B-A22B 的逐专家 983→堆叠 371 ms（2.65×）。稠密 Llama-3-70B 无专家可堆，作者报告 native 调用数两侧相同，不能将噪声较大的耗时差归为堆叠收益。[完整表格和对照设置](https://github.com/NVIDIA/Megatron-LM/pull/8606)。

## 四、要做架构决策，就分别测网络、暂存和版本

以下是建议的工程验收，不是 PR 已经测过的结果。

| 对照 | 固定什么 | 记录什么 |
| --- | --- | --- |
| 消息粒度 | 同逻辑字节、模型权重、训练/推理 EP 与副本数、放置、split 设置 | 原生调用数和消息尺寸分布；端到端 refit p50/p95；每 rank 及每 rail 的实际收发字节、链路忙时 |
| 放置与网络 | 相同拓扑规模和逻辑 rank 图，尽可能只改同柜/跨柜放置；固定堆叠 | 跨柜字节占比、最慢 rank、有效并发链路数、背景流量和同步等待 |
| 显存与转换 | 同权重 dtype、缓冲复用策略；分别测试 view/打包及接收转换 | pack/scatter 与通信的关键路径，暂存 HBM 峰值；目的 tensor/scales 的逐项校验 |
| 权重可见性 | 同一更新窗口、请求集合和版本规则 | 从发布到所有推理 rank 可用的时间；旧请求如何完成、版本混用与拒收数；合格 rollout/s |

只比较总耗时，还会漏掉两种常见反转：其一，通信变快，但 staging 峰值挤掉 KV 或压低生成并发；其二，字节写对，但某个 rank 晚切版本，导致跨 rank 或跨 token 混入两套策略。建议把 pack、通信、落地与可见性按同一时钟打点，区分总和与重叠后的关键路径。还应分开记录首轮、预热后和多次更新循环，不拿一个热态中位数当成所有版本发布成本。

作者在已披露的 refit 验证里以逐 tensor bit fingerprint 对照 send/recv，报告未发现 mismatches；后续四 GB200 rank 针对 Torch MXFP8 数据和 scale 做了覆盖，vLLM/FlashInfer 的两种可选变体被 deselect。**BF16 大表不是低精度 refit 吞吐证明，静态落地位一致也不是在线请求的版本一致性证明。** 后者是[此前 TensorRT-LLM 1.3 解读]({{ '/2026/11/21/tensorrt-llm-130-rubin-moe-rollout/' | relative_url }})也讨论过的另一层。

最后，refit 加速要换算成 RL 总作业收益，首先看它是否在关键路径上。以假设性的完全串行场景为例：若原迭代只有 20% 时间花在 refit，把其中这一段提速 2.27×，整轮提速约为 `1 / (0.8 + 0.2/2.27) ≈ 1.13×`，不是 2.27×。如果 refit 已被生成或训练隐藏，收益可能体现为更低的版本滞后或更多可用 rollout，不一定反映在 step 时间。**先验证传输粒度能否吃满链路，再看这段时间原本挡住了什么。**
