## 1. LiteLLM 1.108.2：修复模型网关的凭证选择与错误回传

**发生了什么：**LiteLLM 发布 1.108.2 LTS，列出 12 项合并变更。其中，修复了 OpenAI 路由部署在 API key 为空时错误使用管理密钥作为 bearer token 的行为，也修复了语音转写错误把提供方完整回复（包括转写内容）回传给客户端与日志的问题。其余修复涉及 Bedrock 服务等级、JSON 格式兼容、缓存路由与数据库重启期间的用量记录等。

**为什么关注：**统一模型网关不仅是 API 格式转换层，也处于凭证、内容和计费信息的交汇处。对已经运行 LiteLLM 的团队，本次更新的价值首先是减少意外的数据流向和配置行为，而不是提高模型分数。这是本文的工程判断。

**边界：**官方发布说明证明的是这些行为被列为已修复，不能据此声称所有部署都发生过密钥泄漏或转写外传，也不能推断已有利用事件。发布说明称升级无需额外操作，但生产部署仍应在自己的配置下验证凭证选择、日志处理、路由和用量记录；这不等同于本站完成升级测试。

## 2. llama.cpp b12191：让 CPU 承担一部分 MoE 缓存未命中计算

**发生了什么：**llama.cpp 的 b12191 预发布构建（GitHub 标记为 pre-release）加入 `--moe-cache-cpu-share`：当 MoE 专家权重留在主机内存、设备端缓存已经填满时，可让 CPU 计算一部分未命中的专家，设备继续处理缓存命中和其余需要上传的专家。同时新增 `scripts/moe-cache-tune.py`，通过不同缓存大小与 CPU 分担比例的实测，拟合机器的传输和计算速度，再推荐参数。

**为什么关注：**运行大型 MoE 模型时，瓶颈可能是专家权重在主机与设备之间搬运，而非纯粹的算力不足。这项改动提供了一种按机器特性调配 CPU 与设备工作的方式，尤其值得显存紧张、专家权重不能全部常驻设备的用户测试。这是适用方向的分析，不是速度承诺。

**边界：**版本文档明确指出，最佳比例取决于机器、模型和缓存大小；主机内存较快、上传链路较慢等条件下才可能更有利。专家权重使用页锁定内存（pinned memory）、能够充分利用传输带宽时，CPU 分担往往无益。该缓存主要面向解码与推测解码等小批量；大批量仍上传所需专家。缓存默认关闭，CPU 分担默认也为零，不能将新参数理解成所有用户自动获得加速。

发布时间：**11 月 7 日 21:11:11 UTC／北京时间 11 月 8 日 05:11:11**，依据 GitHub Release 的 `published_at`，与 tag 或代码提交时间不同。[官方构建记录](https://github.com/ggml-org/llama.cpp/releases/tag/b12191)；[固定在 b12191 的使用说明](https://github.com/ggml-org/llama.cpp/blob/b12191/docs/moe-cache.md)。

## 今日观察

本期的共同点是改善模型周围的运行条件：一个修补网关的数据与配置边界，一个调整专家权重的计算与搬运方式。前者应以回归验证判断是否适合升级，后者应以真实硬件和工作负载测量收益，二者都不能简单换算为“模型更聪明”。
