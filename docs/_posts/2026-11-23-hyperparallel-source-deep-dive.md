HyperParallel 最值得看的是**同一个并行布局如何贯穿算子、通信、优化器与调度**。把参数切给哪些 rank，决定 FSDP 的 AllGather 走哪张网，也决定 Muon 的整矩阵正交化在哪些 rank 上重复做。再往下，同一个 MoE 的通信可以由 PP 调度拿其他 microbatch 的计算来掩盖，也可以把传输与 GMM 拆成 tile，在一颗昇腾芯片内部交错推进。这些是不同层级的优化，收益不能简单相加。

本文以 GitHub 主线 **`6b0e080`（2026-11-22，北京时间）** 为准。区分四种证据：**主线已实现、主线示例或实验路径、独立仓能力、历史论文或生产报告**。代码是静态审阅，未在昇腾实机复跑；所有性能数字均明确对应公开作者的配置。项目名字来自 MindSpore 社区，但当前主线已移除原 MindSpore 后端和平台抽象，直接使用 PyTorch；老版本、MindSpore 生产训练报告和当前 Torch 主线不能混为一谈。[源码快照](https://github.com/mindspore-ai/hyper-parallel/tree/6b0e0800c33e7354215f3866f830ff065230ba20) · [版本说明](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel_v1.0.0_release_notes.zh.md)

## 一、先看调用链：哪些代码属于哪一层

```text
HF 模型/权重 + YAML recipe
  → 模型适配 / 算子替换 / 声明并行布局
  → rank 拓扑与布局，注入 TP / CP / EP / FSDP / PP
  → eager hooks，或受限 FX 联合图 pass
  → torch.distributed + 后端通信 / 昇腾专用算子
  → 可选：独立 HyperMulticore 的片内任务调度
```

同一份仓里还有离线方案搜索、单模型推理工具和实验性 RL，它们不等于普通预训练每一步都会调用的运行时。下文也分别核对了公开示例有没有真正走到被介绍的分支。

## 二、Trainer 与模型适配：怎样把 HF 模型变成一次分布式作业

- 用户选择三类入口，不能混为一个完整 Trainer：①直接导入 Core 并手写训练；② `torchrun ... scripts/train_lm.py <yaml> --training.train_iters=10`，VLM 用 `scripts/train_vl.py`；③原有 VeOmni/LlamaFactory 等集成自己的 Trainer。LM CLI 先解析 YAML，再启动可选 codegen sidecar，然后 TextTrainer；不是通用任务调度器/集群编排。程序式 `models.api.from_pretrained` 委托 CausalLM AutoModel，刻意不 import trainer；上层也可分别用 `HyperAutoModelForCausalLM` / `HyperAutoModelForImageTextToText`。
- 解析：顶层/嵌套 dataclass 处理字段、默认值、类型、路径错误；`_target_` 将 Python 类/函数导入和参数规范化为 `Target`，真正 `build()` 时注入运行时依赖；dotted override 走类型校验，不是无类型字符串替换。模型、优化器、数据集和 collate 等可替换；配置要版本控制、不能把任意外部 YAML 当无执行能力的纯数据。
- `BaseTrainer._setup` 建 process group、选 local-rank 设备、建 DeviceMesh/distributed setup、规范化 override、设种子；HCCL deterministic 环境在建 communicator 前设。然后 AutoModel 原子构建：HF/自定义配置与模型类，替换与元参数准备、tie/freeze、规划并应用布局、激活重算/Swap、FSDP2 生命周期及 shard-aware materialization/loading、最终 model-init dtype，视模式编译。Trainer 不做第二次 parallelize。构建后才挂 loss、tokenizer/processor、transform、dataset/dataloader（支持在线 tokenization、批内 packing、Megatron 格式 Indexed Dataset 等，但要按 recipe）、optimizer、LR、callbacks。模型权重、优化器/FP32 main parameters、scheduler、global step、RNG 与 dataloader cursor 是 DCP 连续性验收对象。
- 声明式边界不是“零适配自动训练”：通用 planner 与模型族语义分开。Registry 扫描 `models/<family>/adapter/registration.py` 或唯一 `*_spec.py`，按 model_type/architecture 归一化名字，惰性加载 provider；后者可声明 replacement、attention/mask/cache、checkpoint mapping 和 export、CP/EP、FSDP wrap/exclusion/execution order、recompute、encoder bridge、special materialization、sharding、loss、reference validation 与 codegen。这解释了为何同一个 HF 模型可以用原生类起步，但高性能路径仍需明确适配，且 family 文件存在不等于全尺寸全并行已验收。
- 另一个机制 `ModuleFamily` 是**构建时**替换：按 `match` FQN、源类型、selector/拓扑挑选白名单实现，选择结果安装到实例，非在每步解释 YAML；若模型/类型不匹配或组合非法则拒绝。新 public GroupedExperts 与旧显式路径不是同一个成员集合，旧固定 MXFP8/fused 示例限制 `TP=CP=EP=PP=1`，不能据此否定独立的 scheme-driven 量化或新低精 EP 路径，也不能把各自支持混写。
- HF loading 支持复用 native Transformers 或登记自定义模型，不能承诺任意 remote code 自动可跑。单独区分 HF 权重初始化、DCP 全状态恢复、DCP/HF 转换、跨切分恢复；模型接入指南要求两阶段，裁剪保留所有层角色且只能标 `cropped_due_to_resource`，完整 checkpoint 则检查 weight coverage、第一步 native 对拍及连续 K+N vs K→DCP→N。同模型同输入/dtype/拓扑的性能 A/B 缺失便记 `PERFORMANCE_INCONCLUSIVE`。HF 权重不含完整训练进度；确定性目标不代表任意模型、拓扑、算子已 bitwise 对齐。

## 三、DTensor 与 HyperShard：生产和布局校验如何共用一份计划

### 物理承载、逻辑布局和 Pending Reduce

- **DeviceMesh**：设备类型、具名维度、shape、rank 网格与 per-axis process group，支持切子网、flatten/unflatten、在规则下 concatenate；底层有内部 shape/stride mesh layout 和 rank map，不是物理拓扑发现或智能路由。比如 mesh 为 `[[0,1],[2,3]]`、名字 `(dp,tp)`，rank 0 的 TP 组是 0/1，DP 组是 0/2。NVLink/HCCS/跨节点实际域仍由放置和 group 对应决定。[DeviceMesh](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/dtensor/device_mesh.py#L143-L238) · [group/submesh](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/dtensor/device_mesh.py#L569-L746) · [concatenate](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/dtensor/device_mesh.py#L1014-L1049)
- **DTensor**：本 rank local Tensor + global shape + Mesh + placements。实际由 `Tensor._make_subclass` 共享 local storage，`__torch_function__` 将操作交给 Hyper dispatcher；`backward()` 委托本地 Tensor，通信能否求导由相应的 torch autograd/collective wrapper 决定。不要写成“框架没有通信反传”。[构造/派发](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/dtensor/dtensor_base.py#L22-L91) · [backward](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/dtensor/dtensor_base.py#L227-L236)

## 四、HSDP 与 Muon：让快网、慢网和优化器各做各的事

### HSDP：把大张量留在快域，对小分片做跨域归约

HyperParallel 的 `fully_shard` 用 1D mesh 做纯 FSDP，用 `(replicate, shard)` 2D mesh 做 HSDP。前向前及必要时反向前在 shard 组 AllGather 参数；反向后在 shard 组 ReduceScatter。只有 HSDP 才把已经切小的梯度沿 replicate 组 AllReduce。把 shard 落在快域、replicate 落在跨域，才能获得这层收益：mesh 配置不是自动测出 fabric，rank 放错，AllGather 还是会出超节点。在 dense/专家场景不必使用同一套组，Trainer 分别选 `fsdp_shard/replicate` 与 `edp_shard/replicate`，对已有 TP/EP 布局可传 `source_shard_infos`。这让“非专家按 TP+FSDP，专家按 EP+专家 FSDP”能保持独立的归约域，而不是把一切压进一条 world group。[接口](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/fully_shard/api.py#L697-L823) · [dense/experts mesh](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/distributed/_builder/fsdp_adapter.py#L140-L183)

按理想等长分片作量纲检查：若每个副本针对某层的梯度是 G 字节、域内 shard 度为 Z，送入每个跨域 AR 的逻辑 payload 是 G/Z 字节，再乘具体算法的流量因子。不要把 G/Z 当成单 rank 网口实测，也不能说全系统跨域流量降了 Z 倍：会同时有 Z 个 replica lane 发流，且可能争同一物理出口。快域与慢域的独立性，才决定多组重叠是否有效。

- **快域，逐参数搬运。** 默认 `comm_fusion=False`；在合适的 dim-0 布局且无需额外 dtype 转换、CPU 搬运或不整除填充时，逐参数 AG 直接写计算所用 buffer，参数是其视图；RS 不需要把多参数 pack、unpack。非 dim-0 用临时 gather buffer 并拼回，梯度也有重排；不整除、offload/类型转换另有实际拷贝，不能称全链路零拷贝。[输入类型/搬移](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/fully_shard/hsdp_param.py#L860-L871) · [AG](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/fully_shard/hsdp_param.py#L1074-L1101) · [RS](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/fully_shard/hsdp_param.py#L1152-L1174)
- **慢域，合并并延迟归约。** 即使 `comm_fusion=False`，HSDP 仍按 replica PG、归约 dtype 组织层内 fused AR；逐参数 RS 直接写到同一 contiguous buffer 的视图，buffer 总长按 512B 上取整，不需要在 RS 和 AR 之间另 pack 一次。默认 interval=1 的反向安排可概括成“收上一单元 RS → 发当前 RS → 异步发上一组 AR → 根回调收尾”，同时可预取下一反向层 AG。它减少慢域等待进入层级关键路径，但链路或硬件并行能力仍决定实测重叠。另一条 `comm_fusion=True` 分桶融合 AG/RS/AR，默认尝试实验性的 AG 输入 flat-buffer alias；必须满足 storage/dtype/优化器条件，否则回到 copy 或 cast，且该路径也可能在后续层同步早期 AR，不应与前一路径当成一个完全无等待实现。[反向调度](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/fully_shard/hsdp_state.py#L277-L417) · [512B layout](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/fully_shard/param_group.py#L932-L1007) · [融合 AG 条件](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/fully_shard/param_group.py#L542-L583)
- **实用接口而非独占功能。** 正/反向预取、前/反后 reshard 开关、分别控制 RS/AR、参数及梯度 dtype 策略、CPU offload，以及 `replicate_params`（保留复制并同步）与 `ignored_params`（完全不管理）的区别，都能在源码找到。PyTorch 2.9 原生 FSDP2 也有 2D HSDP、逐参数 DTensor 表示、分组 AG/RS、前反向预取以及 CPU offload，还有整数 `reshard_after_forward` 中间方案。HyperParallel 有辨识度的是昇腾快慢域的数据路径和时间表，并非“独创 HSDP”。[HyperParallel 指南](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/guide/fsdp.zh.md#L21-L63) · [PyTorch 2.9 原生基线](https://docs.pytorch.org/docs/2.9/distributed.fsdp.fully_shard.html)

### 分布式 Muon：按真实矩阵面决定通信，不是每个 rank 都做一遍 NS

在这个提交里，Muon 从 DTensor placement 构建通信组，再问一个更窄的问题：最末两个矩阵维度是否被切？若仅切专家堆叠轴、每张卡仍持有完整 `[M,N]` 矩阵，专家轴不需为这一步重组整矩阵；若矩阵面被切，则按 layout 对本地动量输入做 fused AllGather，由选出的 shard owner 执行 Newton–Schulz（NS），将 BF16 更新装包后 relay broadcast，各 rank 根据原 layout 切回本地更新。replica 域另有 owner 去重和受限的异步批间广播。当前这条路径节省重复 NS 与非 owner 的结果重组，**并非 owner-only P2P 搬运，更不是没有 gather 的分布式矩阵乘**。[布局分组](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/optimizer/sharding_category.py#L226-L329) · [Gather/owner](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/optimizer/muon.py#L631-L754) · [广播和本地切回](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/optimizer/muon.py#L1107-L1192)

相同矩阵形状拼到 batch 轴共享 batched matmul，而不是把不同权重拼成一张矩阵一起正交化；高矩阵先转置，令 Gram 落在较小维度，预分配工作区。分批元素数阈值按 shard 数缩小，但为了填足 owner 有最小 batch 限制，**是启发式，不是显存硬上限**。逻辑矩阵可交给模型 adapter 决定，例如 V4.1 对指定 Q/K 和 indexer 投影用 head-wise 视图；它与 checkpoint 物理 layout 解耦，不是每个模型自动都按 head 切。Muon/AdamW 可在同一训练中混用，具体选哪些参数、是否用 FP32 master 与内部 opt-state 不应从 “Muon” 名字或某一论文表外推。[NS](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/optimizer/muon.py#L140-L188) · [分批阈值](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/optimizer/muon.py#L935-L969) · [V4.1 adapter](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/models/deepseek_v41/adapter/optim/headwise_muon.py#L26-L64)

[9 月论文 §7.4 表 7](https://arxiv.org/html/2609.21594v1#S7.SS4) 里 16 NPUs 对 DMuon、MatrixFSDP、FlexShard/DistMuon 的**整步** profiler 分别快 5.43%、15.99%、6.19%（rank 0、step 11、各对照一份 trace，不是稳态 E2E 日志）。前两组 HP 的优化器区间反而更长（317.6→605.2 ms、约 394→488 ms），赢在非优化器路径；对 FlexShard 两者用相同 HP FSDP 且对齐 336 Muon/195 AdamW 参数，优化器区间 834.2→527.6 ms，较接近只比较优化器。不要引作全平台排名。

可配置边界有两点：`set_reduce_comm_interval` 要在首个 forward 前设，非融合路径可推迟多个 unit 的 RS 收尾以换取更多重叠，但滞留 buffer 增加；融合路径仅支持 interval=1。[接口](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/fully_shard/api.py#L326-L360) 另外此提交已能组合 **Sinkhorn + Muon + AdamW**：Sinkhorn 对矩阵分片轴聚合行列统计、不在复制轴做 owner 去重，是不同的算法；DeepSeek-V4.1 示例可按 embedding/输出头、其他矩阵、其余参数分类。可选 Gram NS 后端 `gram/gram_quack` 是 CPU/CUDA 路径，符合条件的 Hopper/Blackwell 才使用 Quack，**NPU 输入明确报错**，不是昇腾加速路径。[优化器指南](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/guide/optimizer.zh.md#L141-L237)

对今天的选型，注意 NVIDIA 的 [Megatron-FSDP 官方文档](https://docs.nvidia.com/megatron-core/developer-guide/nightly/user-guide/features/megatron_fsdp.html) 也有 HSDP（内层分片、外层复制）以及不同的 HFSDP（外层还分片优化器状态）；上面 128-rank 比的是 Megatron **DDP+分布式优化器**，不能当成已经对比最新 Megatron-FSDP/HFSDP。建议验收先固定精度、重计算、全局/微批、prefetch 深度和拓扑，在相同 HBM 上限下测同一组有效 tokens/step，再扫 shard 度与通信融合。关键不只是平均 step，还要同图记录 HBM copy、HCCL 暴露时间、host launch/jitter、跨域 AR、EP A2A 和 Muon owners 的最慢 rank。否则某条链路或少数 owner 的尾部可能把节约吃掉。

## 五、CP、EP、PP 和 Mpipe：几种「通算掩盖」各作用在哪

### PP：动态 library 与编译入口不同

- Eager PipelineStage 接收调用者预切的 stage 模块及 PP mesh。GPipe 先全 F 后全 B，1F1B warmup、steady B+F、cooldown；VPP 循环布局 rank r 持有 r、r+P 等多个 stage；支持微批个数小于/不整除物理 stage 数，并不表示输入张量 batch 维可以不整除微批个数。[调度](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/pipeline_parallel/scheduler.py#L1920-L2178)、[微批测试](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/tests/ut/core/pipeline_parallel/test_microbatch.py#L131-L146)。
- VPP 的 `less_memory` 需要显式开启：第 i 个物理 stage 的预发向 slot 数，浅策略 min(V·M,(V−1)·R+P−1−i)，默认把末项改为 2(P−1−i)，R 是首轮微批数。slot ≠ 实测峰值显存。GPipe 与标准 1F1B 在均衡流水的理想 bubble 都约 (P−1)/(M+P−1)，1F1B 首要优势是更早释放激活，不是必然少气泡。理想 VPP 为 (P−1)/(MV+P−1)，实际需算更多 P2P、负载不均和 HSDP/CP/EP 争用。PP8、M8/16/32/64，V1 为 46.7/30.4/17.9/9.9%，V2 为 30.4/17.9/9.9/5.2%。[warmup 源码](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/pipeline_parallel/scheduler.py#L2185-L2217)、[Megatron interleaving 论文](https://arxiv.org/abs/2104.04473)。
- overlap_p2p 与 overlap_b_f 正交，默认都 off。前者早发/收、first-use 才等 handle。后者将 steady-state 的 (B_i,F_i+1) 编成 OVERLAP_B_F，**有注册 callback 才真并发；无 callback 逐个串行**。p2p_transport auto 在 B/F flag 开时默认 gap-time batch duplex，boundary 是可选 F 完成即发；批处理 API 不等于重叠率。enable_dxdw_split 要求 overlap_b_f，把 Wgrad 移到 gap 后，dX 和配对 F 完成后可先发上游梯度。[默认串行](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/pipeline_parallel/scheduler.py#L1155-L1229)、[P2P 配置](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/pipeline_parallel/scheduler.py#L453-L508)、[dX/dW](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/pipeline_parallel/scheduler.py#L1542-L1592)。
- CommComputeOverlap 在 dispatch、FFN、combine、下层 attention 边界用 A/B/C/D autograd hooks，主线程 F + 新线程 B，HookCoordinator 保证 comm-first enqueue。示例 BWD 设线程本地 device，且使用同物理默认计算 stream，利用独立 HCCL stream；示例明确记录改为单独 BWD stream 会破坏 PP recv buffer 的依赖。不是两套计算核心同时执行，也不是 DeepSeek DualPipeV 的 V 形放置。VPP>1 是增加独立调度窗口的常见方法，不是通算同时运行的物理必要条件。实际收益取决于 A2A/算核/HBM/EP 偏斜及跨 rank 时序。[hooks](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/pipeline_parallel/comm_compute_overlap.py#L98-L157)、[示例 callback](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/examples/torch/pp_overlap/pp_overlap_moe_example.py#L252-L344)、[实际注册](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/examples/torch/pp_overlap/pp_overlap_moe_example.py#L400-L450)。
- 独立的 FX 联合图 PpPass 支持 gpipe/1f1b/interleaved_1f1b/vpp，pp_chunks>1 只允许 interleaved。独立 demo 直接构造 PassConfig；不能推断 Mpipe/EP callback 在 Graph 上可用。通用 BaseTrainer 热路径为 graph_compiler.forward_backward 或普通 model forward+loss.backward，未见调用 eager PP schedule；Trainer→PassConfig 也不投影 pp_degree/chunks/schedule。设 accelerator.pp_size 构造拓扑不代表自动跑 PP/Mpipe。[graph PP config](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/compile/pass_config.py#L525-L550)、[graph demo](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/compile/examples/pipeline_parallel/train.py#L130-L159)、[Trainer 热路径](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/trainer/base.py#L881-L926)、[配置投影](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/compile/pass_config.py#L625-L648)。
- 组合证据：[PP+HSDP VPP/dXdW](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/tests/torch/pipeline_parallel/_test_pp_composite.py#L362-L385)、[PP+FSDP+TP 多步](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/tests/torch/pipeline_parallel/_test_pp_fsdp_tp_composite.py#L517-L557)、[VPP P2P 冷启动/NPU](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/tests/torch/pipeline_parallel/test_vpp_schedule.py#L117-L162)。[Llama3 组合 demo](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/examples/torch/llama3/pp_fsdp_tp_cp_sp_example.py#L15-L47) 默认 8 rank 只 PP/FSDP/CP=2、TP=1（SP 没实际分片）；16 rank TP2 是声明配方非本文实测，示例单独 FSDP 轴不能替代通用 Trainer 的 DP×CP 梯度域。

### Mpipe：encoder 独立排程

- 把前置块/视觉 tower 复制到 PP ranks，owner 在 pipeline warmup 空窗内算 encoder，各 rank feature 汇入 stage0：支持 data-load-only T=0，full 轮询分配 overflow，min 让 rank0 接 overflow。默认 trainable encoder 通过 detached output + 原输入回送，stage0 重算反传；owner_backward=True 时由 owner 保图、stage0 回传 feature gradient、owner cooldown 反传、跨 PP SUM tower grad（多次累积只归约本轮增量）。冻结 encoder 不为该段反传保存图。[构造及限制](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/pipeline_parallel/mpipe/schedule.py#L71-L219)、[owner 反传](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/pipeline_parallel/mpipe/executor.py#L414-L491)。
- 明确拒 swap=True，父类 hardcode overlap_b_f=False，不能称 Mpipe+EP B/F overlap 或 PP activation swap 已实现。可透传 overlap_p2p、less_memory。复制权重 HBM、feature P2P fan-in、重算/SUM、视觉长尾仍有真实开销。仓内 [2 rank NPU/Gloo parity 和梯度累积测试](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/tests/torch/pipeline_parallel/test_mpipe_transpose_dist.py#L29-L113)。
- [论文 §5](https://arxiv.org/html/2607.03229v1#S5)：512×910C，Qwen2-VL ViT+DeepSeek-V3、内部数据，作者 DistTrain-like 仿基线（不是实际 DistTrain）16.26→13.42s，1.21×；8×910C，Qwen3.5 MLLM/CapsFusion，与作者采用 Megatron-LM 风格的 baseline 11.01→4.07s，2.70×。都不是 pinned SHA/950 的直接 benchmark，不意味着消除所有模态 bubble。

### CP：分清 QKV、索引和递归状态

- 普通 attention ContextParallel 默认纯 Ulysses，Q/K/V seq→head A2A，输出逆变换，进入 A2A 的 head 数必须可切（GQA 要核 KV heads）。U=1 选 Colossal：保留 Q local seq，AllGather full K/V，可开 head-tail Q 均衡；不是 ring streaming。1<U<C Hybrid 在 Ulysses 子组 A2A，再向另一维子组做 KV AllGather。若本地 KV bytes=X，纯 Colossal 每 rank useful recv=(C−1)X，均衡双向为 2(C−1)X，驻留完整 C·X KV（不含反向/临时），与 ring 可同数量级流量但临界路径和 HBM 不同。[策略源码](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/context_parallel/context_parallel.py#L385-L541)。
- Async 只改变通信投递时间：producer hooks 发，consumer wait。缺 Q/K/V handoff 退同步，接错 PostRoPE/QK norm 边界会跳过后处理，Colossal load_balance=True 回退同步；Hybrid 仅 overlap Ulysses leg，Colossal KV AG 因反向顺序保持同步。CP hooks 不自动切 token、位置、mask；TP→CP→FSDP，CP/TP 可临时组合 mesh 并恢复非 CP 布局，dense 的梯度组覆盖 DP×CP。[async contract](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/context_parallel/async_context_parallel.py#L209-L296)、[组合说明](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/guide/context_parallel.md#L171-L226)、[NPU ST](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/tests/torch/context_parallel/test_context_parallel.py#L99-L165)。
- DSA = DeepSeek Sparse Attention。普通 DSA style 的 indexer/sparse attention/indexer-loss 只支持 Colossal、BSND/TND，带 handoff 的字段可早发 AG。独立 **V4.1 compressed** 路径有 TopK 选择 worker zigzag/greedy/hybrid，attention、teacher、KL 仍在 Q owner；main compressed KV 可 full AG 或因果前缀 A2Av，SWA raw 恒 A2Av halo，Index K 可微 AG。选择均衡要求 CP>1/TP1/MB1/等长 contiguous Q/文档配置一致，不支持后训练候选池，TopK 同分时选中的 ID 不保证位一致。仓内 [1M/128 die 配方](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/examples/training_demo/deepseek_v41/train_deepseek_v41_vlm_1M%20online_128die.yaml#L45-L73) 为 CP128/EP128/PP1；不是规模性能或 PP 全开证据。[通用 DSA](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/guide/context_parallel.md#L124-L167)、[V4.1 细节](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/guide/deepseek_v41_indexer_cp.md#L3-L117)。
- KDA CP 走状态不是 full KV：P2P 传边界 state/逆向梯度；AG 汇总局部 state 与过渡矩阵；grouped AG+P2P 组内 AG、组间 chain；RD 用距离 1/2/4… 的通信合成 affine summary（轮数理论，不保证总时延）；可叠 Ulysses 切 head。B1/H96/K=V128 时单 state FP32 6 MiB、S+M 12 MiB，不是整层峰值。TND 文档 reset 剪枝，保留等长 contiguous、按 rank 序；同时 TP+CP、graph capture 不支持，细分 Triton/AscendC 依赖、数值归约顺序。[KDA guide](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/guide/kda_context_parallel.md#L14-L165)。GDN 另有 [P2P+KV AllGather ST](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/tests/torch/context_parallel/test_gdn_p2p_kv_allgather.py)，不是相同的 KDA protocol。

### EP：新主路径和旧演示必须拆开

- MeshContext 每个 PP stage 的同一批卡复用 dense DP·CP·TP 与 expert EDP·EP 拓扑，N=PP·DP·CP·TP=PP·EDP·EP，不能再次乘 EP。dense FSDP 的 Drep·Dshard=DP·CP，expert FSDP 是 EDPrep·EDPshard=EDP；canonical EPGroupedExperts 接受 dense TP，但专家完整连续 Shard(0)、E%EP=0、ETP=1。[布局约束](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/distributed/mesh.py#L89-L139)、[expert mesh](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/distributed/mesh.py#L308-L403)、[canonical ownership](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/components/modules/moe/grouped_experts/ep/ep_grouped_experts.py#L34-L52)。

- 源 rank per-expert capacity factor 是丢槽，不是整个 EP 域的无损动态迁移。旧 ExpertParallel ParallelStyle / DispatchContext 只留在 examples，公开 PP+EP、B/F overlap example 使用的是旧路径，EP guide 明示移植主路为后续阶段。[指南](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/guide/expert_parallel.zh.md#L5-L33)、[example import](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/examples/torch/moe/parallelize.py#L31-L72)。[MoonEPContext](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/distributed/expert_parallel/moonep_context.py#L24-L124) 只留接口，plan/dispatch/prefetch/combine/reduce_grad 均 NotImplementedError，不同于 fused MegaMoE。
- 均匀路由、无 drop 时每 rank 单次 dispatch 远程 activation 送出 B≈M_local·topk·H·b·(1−1/EP)，combine 一程，反向还要逆传输；TP-extend-EP 中 M_local 用当前 EP rank 真正持有的 token，count/IDs/prob/padding/重算另算。实际 step 要看 max recv/专家时延 p99。

### 原生/Megatron 对照和复测

- [PyTorch 当前 PP 文档](https://docs.pytorch.org/docs/stable/distributed.pipelining.html) 同有 GPipe、1F1B、Interleaved1F1B(flex_pp)、InterleavedZeroBubble、DualPipeV、defer_pp_recv 与 FSDP unshard lookahead；不要把基础调度当 HyperParallel 独占。[PyTorch native CP](https://docs.pytorch.org/tutorials/unstable/context_parallel.html) 在 context 替换 SDPA，提供 pass-KV Ring 的 AG/A2A transport，与换 head 布局的 Ulysses 不同。
- [Megatron MoE](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/moe.html) 已有 parallel folding、AlltoAll/Flex（DeepEP/HybridEP）、EP A2A 邻微批 F/B overlap 和 delay Wgrad、VPP steady P2P overlap；[Megatron CP](https://docs.nvidia.com/megatron-core/developer-guide/latest/apidocs/core/core.transformer.transformer_config.html) 有 P2P ring、AG、A2A、A2A+P2P。HyperParallel 的差异宜写 Ascend 模型和算子适配、Mpipe encoder、KDA/V4.1 特殊 CP 与可插拔 stage，不能宣称首次实现通用组合或直接更快。
- 实验建议：同模型/权重/route trace/seq/GBS/precision/PP EP CP placement，独立消融 overlap_p2p / 真 callback / dX-dW / plain-batch-boundary；设备 trace 与 collectives launch→wait、critical path、HSDP prefetch/RS/headroom、HBM 峰值、p50/p95 step、tokens/s、MFU、全 rank correctness；EP 报 count/permute/dispatch/compute/combine 和最慢 owner，CP 看完整前后向链路/HBM，Mpipe 消融冻结、owner、full/min、视觉长尾和 stage0 fan-in。用实测确认，不以 flag 或平均 A2A bandwidth 代替。

### 私有 SHMEM 与精度账本

- 对称 heap 同一有序 EP Root 内一致顺序分配/释放，PE 是该 Root 局部坐标，不是 WORLD global rank；不相交的各 PP/DP rank 组可独立 bootstrap，每进程同时仅一组 active ordered membership。Push 经远端 put+signal，Pull 由生产方 publish ready、消费者 get，再通过协议确认远端消费。host 返回/stream enqueue、task phase ready、kernel 完成、远端消费完成是不同概念。组内建立/重建仍有 collective/barrier（含 HCCL host barrier）；单边每 tile 不需要对端配对 Recv，但不等于没有同步。push 可能因热点接收容量触发集体扩容/重启，不能以固定平衡 token 基准代替偏斜尾部；需要考虑旧 buffer 读完和 autograd 生命周期。[SHMEM Root](https://github.com/mindspore-ai/hyper-multicore/blob/a80d1287547fe29190837329c12cbd6eebe854cd/docs/shmem.md#L151-L184) · [通信语义](https://github.com/mindspore-ai/hyper-multicore/blob/a80d1287547fe29190837329c12cbd6eebe854cd/docs/shmem.md#L199-L241) · [Push/Pull](https://github.com/mindspore-ai/hyper-multicore/blob/a80d1287547fe29190837329c12cbd6eebe854cd/docs/shmem.md#L376-L411) · [扩容](https://github.com/mindspore-ai/hyper-multicore/blob/a80d1287547fe29190837329c12cbd6eebe854cd/docs/mega_moe.md#L310-L327)
- 当前锁 CANN SHMEM v1.8.0，runtime 与日志适配补丁，按 arch 装载私有 SONAME，不等于 CUDA NVSHMEM，也不等于所有集体通信走 SHMEM。已列构建目标 ascend910b/ascend910_93→arch22（BF16，MTE），ascend950→arch35（BF16 与 MXFP8，默认 mte_udma、可选 MTE、该默认 UDMA QP=1）。链接/拓扑能力不从传输引擎名字推出；没有证据表明该 op 的 peer 数据面跨 UBG/任意以太网络就等价工作。[构建目标](https://github.com/mindspore-ai/hyper-multicore/blob/a80d1287547fe29190837329c12cbd6eebe854cd/docs/build.md#L123-L159) · [SDK 锁及加载](https://github.com/mindspore-ai/hyper-multicore/blob/a80d1287547fe29190837329c12cbd6eebe854cd/docs/shmem.md#L397-L446)
- **MXFP8 fused compute ≠ FP8 dispatch**：MXFP8 入口和通信从 BF16 hidden/gradient 起步；前向 dispatch 完才对专家 input 双轴量化，GMM1→SwiGLU+量化→GMM2→combine。反向 quant_dy，分别给 dW2/dA；SwiGLU grad+双轴量化，再 dW1/dX→combine。各自使用 OCP 式 E4M3 payload 和 `uint8` E8M0 scale（每 32 元 1 scale，配对存储成 64 元组末维2），权重前向 col_data/col_scale、反向 row_data/row_scale，FSDP 当前 gather 后更新同一 root；不能把两个方向的一份 FP8 换 dtype 复用。单轴约 1.03125B/slot，两个方向同时常驻约 2.0625B/slot，未算 BF16 master、padding 或释放/重算，因此只说单向量化页、而不是两轴常驻都 2× 省 HBM。对 comm 模型仍先按 BF16 payload，profiling 证实后再降价为 FP8 bytes；这里只是降低 GEMM 精度及若干本地数据字节。[MXFP8 图](https://github.com/mindspore-ai/hyper-multicore/blob/a80d1287547fe29190837329c12cbd6eebe854cd/hyper_multicore/modules/mega_moe/backends/mxfp8/graph.py#L116-L180) · [运行现场 BF16 dispatch](https://github.com/mindspore-ai/hyper-multicore/blob/a80d1287547fe29190837329c12cbd6eebe854cd/hyper_multicore/modules/mega_moe/backends/mxfp8/execution.py#L64-L109) · [权重布局](https://github.com/mindspore-ai/hyper-multicore/blob/a80d1287547fe29190837329c12cbd6eebe854cd/docs/mega_moe.md#L169-L201)

### 论文结果应如何引用

[HyperParallel-MoE 论文 §§4–6](https://arxiv.org/html/2605.23764v1) 为 2026-05-22 v1。纸面词汇 ODG→tile task TD→CTQ/VTQ/event counters→SSC，运行时复用 fixed shape bucket/EP/rank 的计划；AIV put_mem_signal 允许按就绪 tile 消费；RATR 旋转目的 rank（减瞬时热点，不减少总字节），反向按 expert 交错可复用激活的 GMM task（争取 L2）。原型是 **MindSpore/MindFormers**，与当前 Torch 产品路径有机制继承但没有同 commit 复现等号。256 A3 profiling 中 GMM 平均 MAC 利用率约 67%、关键 Vector ~18% 总时、EP 通信约 17%，约 61% EP 通信可隐藏；与 64 A3 benchmark 是两组实验，不可混算。主对照 64 A3、每设备 25 AIC/50 AIV、192 MB L2，DeepSeek-V3-style BF16 FFN，S4096/MBS2/H7168/I2048/top8/Gbs512，DP32/TP2，EP4/8/16 各 8 本地专家、总专家数 32/64/128，编译排除在 module timing 外。

### DeepEP / DeepGEMM 比较与验收建议

- 通常所说 **DeepEP** 是单独的 dispatch/combine EPBuffer API，GPU V2.5 可异步、deferred epilogue，framework 在消费时 wait，并可重叠独立的工作；当前 CUDA 主分支用 NCCL Gin，不要沿用 V1 NVSHMEM 描述。它不是整个 GMM-SwiGLU-GMM 的优化。最近的同层对手是 **DeepGEMM Mega MoE** 的单 CUDA kernel 组合 dispatch→linear1→SwiGLU→linear2→combine，NVLink 与 Tensor Core overlap，外层负责 symmetric buffer、路由、输入准备，现在文档支持 FP8×FP4 与 FP8×FP8。不要称 DeepEP 只有 NVIDIA；**DeepEP-Ascend** 是可对比的 EP 通信库，提供 950DT 上 FP8 dispatch/BF16 combine 和 deferred epilogues，而非这套 AIC/AIV 整条 FFN 调度。其 CANN 9.2.0/PoC HDK/netlayer1/16,384 token capacity/top6 的公开数只覆盖通信 issue→drain、排除最终 epilogue，不可与论文 Dispatch→Combine 前反向比较。[DeepEP](https://github.com/deepseek-ai/DeepEP) · [DeepGEMM](https://github.com/deepseek-ai/DeepGEMM#mega-moe) · [DeepEP-Ascend](https://github.com/deepseek-ai/DeepEP-Ascend#performance)
- 我建议基准做同一 950DT、EP 与网络路径、同 router trace 和 H/I/top-k/有效 tokens（限时给平衡/长尾两种），以 **BF16 native EP→BF16 MegaMoE（MTE/UDMA 独立开关）→MXFP8 MegaMoE** 拆贡献，前提是数值语义一致；模型若依赖 clamp，MXFP8 MegaMoE 不适合作直接替换，用 GroupedExperts 的局部验证单列。记录 dispatch/combine 有效字节（单向与 TX+RX 分开）、fwd/bwd 模块边界、完整 step、p50/p95 最慢 rank、AIC busy、AIV/依赖等待、L2/HBM bytes、UDMA QP/信号等待、SHMEM workspace 峰值及扩容事件。分开测 fixed plan 稳态与 cold build/restart，输出/梯度及优化轨迹和长尾性能并列。对比 GPU MegaMoE 不必抹平设计差异：先单平台比较本地方案相对 baseline，再讨论是否能迁移“每 expert ready 即推进”和“分开通信/数学队列”。

## 七、激活、状态和 checkpoint：三种省 HBM 的机制

### 激活如何留、算、搬
- **手工框架级/算子级**：在 [Activation Memory 指南](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/guide/activation_checkpoint.zh.md) 用 `checkpoint_wrapper` 包 module/callable；SAC policy 在被拦截算子上区分 MUST/PREFER_SAVE、MUST/PREFER_RECOMPUTE、MUST_SWAP，分别代表缓存输出、反向重算、前向写入 host / 反向取回；`swap_inputs` 还能搬 checkpoint 保存的输入。局部昂贵块可 `checkpoint_exclude_wrapper`：首次执行并保留必要输出/反向图，重算阶段按配方回放，而不是再次运行该块；不在外层 active checkpoint 时透传。纯 swap（不重算）可用 `swap_wrapper`，显式大 tensor 可用 `swap_tensor_wrapper`。`SwapManager.set_forward_prefetch_layer` 手工注册层间关系（不必相邻）；group_swap 可尝试将 MUST_SWAP copy 成组；它不是“无需用户配置的全局 planner”。[policy](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/activation_memory/policy.py) · [SAC 执行](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/activation_memory/sac.py#L145-L265) · [SwapManager](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/activation_memory/swap.py#L1064-L1155)。
- **eager 自动 activation residency**：[OffloadSession](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/auto_parallel/hyper_offload/api/session.py) 包住 forward+backward；首轮跟踪 tensor storage/依赖并 eviction，之后由 [greedy planner](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/auto_parallel/hyper_offload/planning/greedy.py) 结合预算规划，再 replay 驱动分离 stream 上的 D2H/H2D、device/host buffer release。目标预算是被管理激活的驻留量，不是承诺整卡峰值小于给定值；权重、optimizer、workspace 和水位均另计。[README 限制](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/auto_parallel/hyper_offload/README.md#L148-L153) 明说单设备、跨 rank FSDP/TP/PP 联合规划是未来工作，warmup/replay 需匹配，动态区域可标 skip_offload；[replay](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/auto_parallel/hyper_offload/execution/replay/executor.py#L50-L100) 有执行差异检查。
- **FX 计算图插入**：[CpuOffloadPass](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/compile/passes/cpu_offload.py#L15-L53) 证明不能说“公开仓没有图级插入”：top-level `activation_swap="attention"` 可选 self_attn 中被 BWD 使用、独立拥有、连续、无 in-place 写且满足容量条件的对象；对 storage alias 去重，生产后发 `ao.offload`、最后 FWD 读后 wait/release、BWD 前 `ao.reload/wait`，可提前若干 attention region 发 H2D。这条局部 host pass 在 FSDP pass 前，与其配置级 AC 互斥；不能用它否定上方手工 API 允许同一模型配置 recompute+swap。1 MiB 是此 pass 的候选阈值，不是最佳值的硬件定律；无法获得 trace-time size hint 的动态大小会跳过。

### 参数/优化器 CPU 路径和磁盘 checkpoint
- [HSDP CPUOffloadPolicy](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/fully_shard/utils.py#L307-L319) 是 rank 本地 host storage：参数 shard 在 all-gather 前 H2D，梯度 backward 后回到 CPU，可 pin；与激活 swap、GPU/NPU peer 内存均不同。
- [Adam swap](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/optimizer/swap_adam.py#L36-L67)、[Muon swap](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/optimizer/swap_muon.py#L91-L122) 有真实状态 adapter，搬 Adam moments、Muon momentum，独立的 [swap runtime](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/optimizer/swap_optimizer_base.py#L244-L325) 提供一批前瞻/packed pipeline；不能说该功能只是论文愿景，也不能说自动 OffloadSession 已自动管理这些对象。[RL 训练态 phase offload](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/rl/rl/workers/engine/offload.py#L59-L147) 另有显式空闲边界、权重和 optimizer state 到 CPU / restore，属 rollout/trainer 时间复用，不是跨 rank 内存池。
- [DCP](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/guide/distributed_checkpoint.zh.md) 保存状态字典、布局变化时重分片加载、可做离线格式转换，storage I/O 是 checkpoint 读写，不是每 step 将 working-set swap 至 NVMe。[async_save](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/core/distributed_checkpoint/api.py#L315-L399) 的 staging 在调用进程同步拷到 host；异步的是后台子进程里的规划/collectives/磁盘 I/O，应等待 persist_completion。与激活 checkpoint（省显存，训练过程中无落盘）完全不同。没有在本快照核实通用 NVMe 在线 offload manager。

### 论文的超节点内存池，主线实现到哪了
[HyperParallel 总体论文 §3.2](https://arxiv.org/html/2603.03731v1#S3.SS2) 中，作者曾描述 HBM 是外部内存池前端，经预测提前读入缓存块，MindSpore JIT 全图插入 cache operators 并调度计算、网络与存储。本文仓中查到的是上列本地 host pin/offload、FX 插入及 rank 内工具。未找到通用远端 tensor residency/对等 HBM 或跨节点 DRAM global allocator + 远程 prefetch 的可运行 API/实例。参数 all-gather、Mpipe P2P、DCP 跨 rank 读取都不是远端缓存管理。论文报 Llama-8B 5.2s→4.08s = step time 降 21.5%、等工作量吞吐 +27.45%，等 latency 上下文 71K→123K 是约 +73%；论文未在该段给出可独立重跑的完整硬件/对照与命令；不能归因给这里任一公开 API，也不能外推到任意训练作业。

### 怎么测是否值回搬运成本
每层 S 字节实际 offload 总 traffic 约 S D2H + S H2D，各自按实测方向有效带宽和各自 copy window 单独估时；并行时还共享 host DRAM、DMA/PCIe 或片间链路，不能把铭牌双向带宽分别套给两个方向。选择性重算与 swap 的比较至少同 microbatch 和模型精度做 HBM 峰值、同步暴露时长、step latency/token throughput、MFU 及 host pinned DRAM 水位；同时打开 CP/EP/HSDP 查看 tail、拥塞和 copy overlap。CPU/disk checkpoint 测量分别报 staging stall、持久化完成延迟、reload/reshard 恢复时间；不能用后台存盘时间冒充 step 上额外等待，也不能用单卡 peer 带宽冒充全超节点 offload BW。

## 八、自动并行不是一个黑盒：SAPP-ND 和 PPB 回答不同问题

**SAPP-ND 回答「这次作业该用多少 TP/CP/EP/PP，什么配置能放下」。** 它把模型的尺寸、层类型、算子谱（`ModelSpec`）与一次运行的并行度、序列长度、优化器、精度、重算（`ExecSpec`）分开。搜索器枚举允许的离散维度，检查设备数、batch 等约束；先按估算峰值显存过滤，再按解析步时模型排序。模型可以从 HF config 或模型族算子表构建，也可通过 fake layer census 补充某些层的算子/张量信息；其意义是量形状和生命周期，不是实机 profile。若训练器支持相应字段，输出可回写成 `resolved.yaml`；不支持的逐层重算结果只能作建议。[搜索逻辑](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/auto_parallel/sapp_nd/nd/parallelize.py) · [输入与校准](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/auto_parallel/sapp_nd/README.md)

**SAPP-PPB 回答「PP 框架已定，哪几层放哪个 stage，哪里要重算」。** `PPOptimizer` 读 YAML 拓扑和约束、JSON 层 profile，把 HEAD/BODY/TAIL、虚拟 stage、重算与显存上限交给 `PPBalancer` 做整数规划；接着可让 `PPSimulator` 用解去重放 step，估 bubble 与峰值。求解器找到可行方案，和仿真成功或方案在真机上最快，是三个状态。工程上应按 Top-K 上机，不只跑估算第 1 名；同时收集慢 rank 的 P95 step、各域带宽、专家路由 skew 以及 allocated/reserved 的差。尤其不要把 A3 的 sustained TFLOPS、链路或 allocator 余量拟合直接移植到另一种超节点。[优化器](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/auto_parallel/sapp_ppb/pp_optimizer.py) · [整数规划适配](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/auto_parallel/sapp_ppb/pp_modeling/pp_balancer.py)

差异化在于**快速搜索与实际 recipe、层 census 和实测对账接在一起**。它没有解决数据依赖路由、运行时 NCCL/HCCL 竞争、极端碎片和长尾。只要这些量改变候选排序，成本模型就要重新校准；离线估计本身不能证明比人工调优或其他搜索器领先。

## 九、动静结合：联合图能排什么，现在哪些还不能排

`GraphCompiler` 用 FakeTensor/`make_fx` 对训练函数做联合图捕获，参数是占位输入，反向来自 `autograd.grad`。Pass 顺序有实际含义：先做死代码清理、规范化和激活保存/重算，再由 FSDP 在首次读参数前插 AG、最后读后释放、反向前按需再 AG、梯度端接 RS/AR；然后做桶化与 FSDP 特定重排。最终才按 stage 切 PP 子图；否则图级 pass 只会看到调度 stub。Inductor 在终端处理计算区域或每个 stage 子图，PP P2P 仍留在外面。[联合图文档](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/compile/README.md) · [实际 Pass 顺序](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/compile/passes/pipeline.py#L99-L141)

这里有一个容易读错的开关：通用 `AutoOverlapPass` 虽会找到 `wait_tensor`，**移动函数现在原样返回**；真正推早 AG、把 wait/view 沉到依赖处、重排梯度归约的是 `FsdpOverlapPass` 的两个独立开关，AG 受在途内存预算约束。图分区会修改活模型，不应重复 compile；增强的联合捕获依赖 patched autograd，stock Torch 有结构性标注回退；动态形状不能与 PP 同开；此图路径的 EP、PP+HSDP 和 PP+TP 不按 eager 的能力计算。Inductor 扩展依赖相应 Torch 接口，老构建可能明确保持 eager。[Overlap 实现](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/compile/passes/overlap/schedule.py#L39-L125)

## 十、RL 与推理：真正的边界是策略发布，不是 decode 峰值

实验性 **HyperParallel-RL** 用 HyperParallel 训练、native-vLLM 采样；同步路径围绕 rollout、学习、权重发布、评估、checkpoint 编排。轨迹保存生成时的 token、logprob、动作掩码与策略版本，工具输出和观察能进上下文但不进入 policy loss。发布新策略前先等 HSDP、重分片并回收缓冲，按桶 `full_gather`，同卡用 IPC、分离设备用 HCCL；收到确认后才回收临时缓冲并恢复 rollout。关键是行为策略和学习侧能对账，而不是从日志文本重新分词。[同步编排](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/rl/rl/trainer/sync.py) · [发布边界](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/rl/rl/weight_sync/publication.py) · [轨迹合同](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/rl/rl/data/contracts.py)

单节点 rayless 异步路径有在途请求预留、版本分段与超龄组淘汰；实验性同卡异步路径还有限定的 CPU offload、`reshard_after_forward`、vLLM sleep/eager 和采样参数。PPO、Agentic 轨迹、奖励模型、单/多教师蒸馏有各自的配方，不等于可与所有异步、MoE、分离部署选项任意组合。README 明确提醒现次重构未继承历史设备验收，checkpoint schema 2 不兼容历史快照。另有独立 `infer/` 实现基础 prefill/decode、采样、KV cache 和 TP/CP logits gather；RL 主采样路径是 vLLM，这套普通生成工具不等于服务级 backend。[异步接纳与淘汰](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/rl/rl/async_runtime/protocol.py) · [支持矩阵](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/rl/README.zh.md#支持范围) · [推理实现](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/infer/generation.py)

比较它与 veRL 等系统时，我会先固定模型、每题候选数、采样参数、奖励和验证集，再量**达成同等 reward 的墙钟时间和设备小时**。同时拆出有效生成 tokens/s、合格轨迹/s、训练更新/s、权重切换和工具等待；异步再加 policy lag、废弃率和训练/采样卡的独立利用率。仓内历史 GSM8K 与 veRL 的设备显存、软件版本和采样修复状态不同，不能把 reward 差或 decode 差直接归因给框架。[项目实验与限制](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/rl/README.zh.md#-快速开始)

## 十一、规模证据怎么读，以及我会先验什么

**DeepSeek-V4.1-Flash：跑通模型结构，不等于跑完公开默认规格。** 项目用单机八张 64 GiB 的 910B3、随机初始化裁剪模型与合成数据；文本策略完成六步，TP1 / TP2+SP / CP2 分别约 1,675 / 847 / 1,407 有效 tokens/s，峰值 allocated 39.08 / 24.42 / 20.65 GiB。CP2 比 TP1 少约 47% allocated，但平均 step 19.57→23.30 秒。多模态十步是另一个裁剪配方，不能与文本 step 横比。这个结果说明模型适配（跨层 KV、Engram、mHC 等）能接上分布式路径；不能当全尺寸训练 MFU、长跑收敛或恢复证明。[项目原测与边界](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/docs/deepseek_v41_article/README.md#4-results-training-metrics-and-model-correctness-validation)

**Xing 4：规模应用与对照 profile 分开看。** 报告称 285B 成员生产预训练用 8,192 张 910C，表 7–10 则是 1,024 NPU profiling。262,144 序列、GBS 16、TP4/EP64/CP32 固定时，PP 1F1B 36.4 秒、VPP 34.2 秒、HSDP/PP1 31.8 秒。它同时改变了 PP/DP 和 microbatch，不能把整段差值写成某个 kernel 的加速。Owner Muon（28.9 秒）、细粒度重算（26.9 秒）、逐层 Indexer backward（24.5 秒）按不同对照读：9.1% 用 31.8 秒作分母，后两项各自用 28.9 秒作分母。不能把 9.1%、6.9%、15.2% 直接相加，也不能把生产报告里的 owner P2P 实现当成主线公开 Muon 的通信算法。[Xing 4 技术报告 §3、表 7–10](https://arxiv.org/abs/2611.22115)

我会先验三件事：

1. **看哪张网的等待暴露在关键路径。** 同模型、同有效 token、同精度做 1/2/多超节点阶梯测试。改变拓扑映射和 replica/shard 比例，分别量 AG/RS/AR 的搬运字节、HCCL 时长、同域并发后的有效带宽、临界路径等待与峰值 HBM。再与同等预取、同等 bucketing 的原生 FSDP2/HSDP 比。比较用 NPU-hours/十亿有效 token 与 P50/P95 step，而不是总线上见到 overlap 就认为有效。
2. **把数学等价和系统收益拆开。** 对照逐层输出/梯度范数、各布局 loss、优化器更新差异和恢复续训；Muon 另外量通信、NS 矩阵计算、去重收益、峰值驻留。PP/EP 同时检查 loss、route skew、SM 或 AIC/AIV 占用、A2A 的纯通信和掩盖后剩余。要算 MFU，分子用模型有效 FLOPs（MoE 激活专家，加实际 attention 路径等），不把重算、padding、无效 token 或 optimizer NS 当成模型有效算力；分母标清设备数与精度峰值。
3. **寻找拐点而不是单个最好数字。** 分别扫描序列长度、路由偏斜、PP microbatch 数、CP/EP group、重算与 pinned host 带宽。盯住 PP 被 HSDP 替换后新增的跨域同步，和 tile 融合之后增长的驻留或抢占。做确定性对照时固定拓扑、kernel、版本和数据顺序；种子、HCCL 确定性开关和 `warn_only=True` 不构成任意配置逐位可复现，也不能代替训练态 SDC 校验。仓内另有可选 AIC/HCCS 算子 stress callback，依赖 `torch.npu.stress_detect`，模型级 stress detect 仍保留未实现，不能把硬件压力探针当成模型级 silent error 的全覆盖。[Stress callback](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/trainer/callbacks/stress_detect_callback.py) · [配置限制](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/trainer/config/stress_detect.py#L59-L79)。[Trainer 确定性控制](https://github.com/mindspore-ai/hyper-parallel/blob/6b0e0800c33e7354215f3866f830ff065230ba20/hyper_parallel/trainer/runtime/random.py)

**最终判断：** 最有工程辨识度的是分层 FSDP、布局驱动 Muon，以及少数确实落到设备内的 MoE 通算路径；其次是 DSA CP、多模态转置和模型适配，解决的是现成系统不易覆盖的组合。TP、常规 PP、普通 checkpoint 和接口齐全属于必要能力，不能单独冠以领先。要兑现超节点的优势，关键是设计和实测都能回答两件事：**通信有没有留在更快的域，等待有没有从关键路径消失。**
