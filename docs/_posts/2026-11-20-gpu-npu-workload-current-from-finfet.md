先猜一道题：同一张 A100 跑 FP16 矩阵乘，把输入从全零换成随机数。仪表上的功率会不会变？[SC25 论文表 2](https://escholarship.org/content/qt6189368s/qt6189368s_noSplash_8589457fdac04188de748390daac1128.pdf)给出的答案是：**271 W 变成 400 W，吞吐反而从 291 降到 263 TFLOP/s。**

要解释这个结果，不能从“GPU 利用率几成”开始。得往下一层：**这批指令让哪些电路翻转了、翻转多少，以及这些活动在时间上有多集中？** 这三件事分别通向平均功率、能效和供电可靠性。

## 第一课：FinFET 是开关，负载给开关安排工作

把典型三栅 FinFET 想成一条竖起的硅鳍。源极和漏极在通道两端，栅极隔着绝缘介质控制鳍的顶部和两个侧面。以 NMOS 为例，栅相对源的电压升高，沟道更容易导通；电荷主要走源漏通道，**不需要从栅穿过绝缘层流入通道**。栅本身仍有电容，要靠上一级电路充放电。三面控栅的价值是更好的静电控制：抑制短沟道效应，在设计工作点上改善导通、漏电和电压之间的取舍。它并没有规定一次 GEMM 会吃多少安培。[Intel 的器件说明](https://www.intc.com/news-events/press-releases/detail/655/intel-reinvents-transistors-using-new-3-d-structure)

接下来把 PMOS 和 NMOS 接成 CMOS 反相器。节点负载电容 C 包含下一级栅电容、连线等寄生电容。这里先假设输出在 0 和 VDD 之间完整摆动：

```text
输入变低：PMOS 导通，电源 → 输出节点，给 C 充电
输入变高：NMOS 导通，输出节点 → 地，C 放电

一次充电：电源送出 Q = C × VDD
电源做功：VDD × Q = C × VDD²
```

充电结束时只有 ½CVDD² 存在电容里，另外一半在充电路径中耗散；随后放电，存下的那一半也在放电路径中耗散。**对理想 CMOS 而言，一次完整 0→1→0，电源一共送出 CVDD²，并不是只送出 ½CVDD²。** 按每周期平均发生多少次 **0→1 充电**定义活动因子 α，频率为 f，忽略其它项，则：

```text
I_switch ≈ α × C × VDD × f
P_switch ≈ α × C × VDD² × f
```

这是单个节点的平均值。同一条电源轨上要把各节点的贡献加起来；不同域电压、频率不同时要分别算。实际还有漏电，输入越过转换区时上下管短暂同时导通的电流，以及时钟树、保持与刷新等背景成本。时钟门控可以让部分不干活的电路少切换；只停时钟，并不会消掉漏电。[MIT 6.012：CMOS 动态功率](https://ocw.mit.edu/courses/6-012-microelectronic-devices-and-circuits-fall-2005/resources/lec14/)

**随堂题：**同一节点 C＝10 fF、VDD＝0.8 V、f＝1 GHz，α 从 0.1 变 0.4，平均开关电流从 0.8 μA 变 3.2 μA；从 0.8 V 降到 0.7 V，若活动和频率不变，动态功率约降 23%。这是算式示例，不是现代芯片的节点参数。实际降压往往还得调频率，不能只拿平方律算整卡节能。

## 第二课：一个 Tensor Core 或 Cube 指令，内部没有“固定翻转次数”

一条矩阵乘指令可能触发寄存器和 SRAM 读取、操作数搬运、乘法阵列、归约或累加、结果写回。输入变了，部分积、进位、尾数和累加器的位模式都可能变；同一块电路在两拍之间切换的节点数就会不同。**关键是相邻状态的变化，不是单个数里有多少个 1。** 重复传同一个全 1 字，数据线未必反复切换；在两个值之间交替，则可能每拍都翻很多位。真实内部节点还有进位、毛刺、编码和门控，因此输入 Hamming 距离只能做线索，不能直接换算成功率。

再往外一层，一次新请求可能把数据从 HBM 拉到缓存、片上网络、共享存储或寄存器，也可能复用已经在片上的数据。即使 FLOP 数相同，经过的物理路径不同，活动总量也不同。把这层写成能拟合的工程近似：

```text
设备功率 ≈ 背景功率(温度、电压、频率)
         + 矩阵执行率 × 有效 J/op
         + 向量执行率 × 有效 J/op
         + HBM 实际读写率 × 有效 J/byte
         + 链路实际收发率 × 有效 J/byte + 残差
```

这里是**同平台、同测量边界、局部工作点**的模型。把实际做过的工作与业务有用工作分开：padding、低填充 tile、投机拒绝、重计算都可能消耗硬件资源，却不一定增加有效 token。系数混合了相关路径的活动，不能当成某个单元装了电表；达到功率上限、改了频率或发生争用后，系数和活动率都可能变。[SC25 的活动率建模及归因方法](https://escholarship.org/uc/item/6189368s)

回到开场题。论文使用厂商工具监测设备报告的功率，采样节奏约 1 秒；下表只取 Table 2 的 FP16 HGEMM。能量列由报告功率除以名义 FLOP 速率计算，不是矩阵单元本身的能耗。

| 平台 | 全零：W / TFLOP/s | 随机：W / TFLOP/s | 随机相对全零的 J/名义 FLOP |
|:--|--:|--:|--:|
| NVIDIA A100 | 271 / 291 | 400 / 263 | 1.63× |
| NVIDIA GH200 | 578 / 875 | 854 / 757 | 1.71× |
| AMD MI300A | 550 / 463 | 550 / 355 | 1.30× |

**MI300A 这一行尤其值得看。** 瓦数完全一样，做同一批名义工作却要多花约 30% 能量，因为吞吐下降、用时延长。A100 和 GH200 的观测与数据相关开关活动、功率约束改变工作点的解释一致，但表中看不出哪个模块具体多耗了多少，也不能把全零拿来预测真实模型或当成稀疏加速的证据。

## 第三课：看 workload，先问“是哪个域忙”

以下是相同平台下的**预期活动分布**，不是跨设备的功率排序。一个通信受限任务可能核心电流较低，却拉高 I/O 侧负载；一个 HBM 受限任务也可能接近整卡功率上限。

| 负载 | 电路和时间上的变化 | 要一起看的信号 |
|:--|:--|:--|
| 大 GEMM、训练里的饱满矩阵段 | 连续喂满矩阵阵列、寄存器和片上搬运，核心容易形成高平台；尾 tile、小形状和取数断流会改变平台 | 实际矩阵执行率、设备/核心频率、温度、限功率状态 |
| 向量、归约、优化器更新 | 矩阵阵列可能空闲，向量、片上缓存、HBM 或同步路径仍工作；融合会改变中间读写和波形 | 向量执行率、实际 HBM R/W 字节、kernel 边界 |
| 长 prompt 的 prefill | 一次处理多个 token，权重更易复用，矩阵与 attention 活动常集中；不同长度和 attention 实现不一定同一瓶颈 | prompt 长度、实际计算/访存、TTFT |
| 小 batch decode | 每步只产生少量新 token，权重读取和随上下文增长的 KV 访问可能占主导，核心活动常呈间歇；对单步延迟敏感 | batch、上下文、实际读写、TPOT、J/输出 token |
| 大 batch、MoE 或投机 decode | batching 提高权重复用；MoE 路由和 EP 搬运增加负载偏斜；多 token 验证可能重新把矩阵域激活 | 每 rank 有效/填充/执行行、链路字节、提交 token 数、p95 TPOT |
| AllReduce、EP All-to-All、CP 交换 | DMA、链路 PHY 或执行通信 kernel 的核都可能参与；与 GEMM 重叠时，多个域可同时耗电 | 每 rank 双向链路字节、等待/重叠区间、峰值 rank |
| PP 气泡、屏障、空流量 | 计算域停下来，但设备未必关电；时钟、HBM 刷新、I/O 背景活动仍在 | 空闲基线、停顿时长、各 rank 是否同步 |

如何从模型参数快速判断？用算术强度做第一步：**实际执行 FLOP ÷ 实际搬运字节**。权重每读一次能服务更多 token 时，比同一批权重为每个小请求反复读取更容易把计算单元喂饱。例如一个理想化 BF16 线性层，每个权重 2 字节，每个 token 对该权重做一次乘加（2 FLOP）。忽略激活、输出和 KV 流量，若同一权重从 HBM 读一次、复用 B 个 token，则按权重流量的算术强度约为 B FLOP/byte：B＝1 对应约 1，B＝32 对应约 32。实际计算仍要加上其它流量、tile 重读和缓存命中。

但 Roofline 只能帮你判断吞吐可能被哪条资源线限制，不能当功率曲线。比如两个 decode 都被 HBM 卡住，一个还大量扫长上下文 KV，另一个通过缓存减少请求，它们的内存与链路活动未必相同。

**实测支持什么？** [ASPLOS 2024，§4 和图 4、6–8](https://www.microsoft.com/en-us/research/wp-content/uploads/2024/03/GPU_Power_ASPLOS_24.pdf)中，A100 训练实验的迭代边界，RoBERTa、GPT-NeoX、Flan-T5 的功率分别降至约 75%、50%、20% 的 TDP。另一些推理实验观察到 prompt 阶段较高、后续生成较低而平稳，测试中 batch 变大也抬高平均功率。**20% 不是通信阶段的固定功耗，75% 也不表示通信本身吃掉了这部分功率。** 这些值包含了当时仍在运行的其它设备活动，比较对象、并行策略和阶段边界都很重要。

两个工程推论：

- **更高的平均瓦数也可能更省电。** 假设同样产出 10,000 token，方案 A 300 W × 10 s＝3,000 J，方案 B 360 W × 7 s＝2,520 J，B 的 J/token 降低 16%，但对局部供电和散热的功率预算更高。只有在输出质量、服务条件和计量边界一致时，这类比较才有意义。
- **位宽减半，不能推导整卡电流减半。** 低精度可减少部分权重字节和计算路径翻转，却也可能包含反量化、scale、转布局、宽精度累加或额外通信。效率提高后，单位时间发射更多操作，也可能使平均瓦数不降反升。对照时同时报同吞吐下的瓦数，以及同功率限制下的吞吐、质量和 J/token。

## 第四课：核心 500 A、板卡十几 A，怎么能同时成立？

这里要先画清计量边界：

```text
机柜/服务器供电 → 模组输入 → VRM/稳压转换 → 核心、HBM、I/O 等电源轨
       PDU          输入表                芯片附近测点
```

假设**只有核心轨**就消耗 400 W、该轨电压 0.8 V，则在稳定近似下核心轨电流是 500 A。这不是把“板卡遥测 400 W”换算出的结论。另假设整个模组输入是 600 W、输入电压 48 V，则该输入处是 12.5 A；不矛盾，因为稳压器转换电压与电流，且另有负载和转换损耗。加总不同电压轨的能量或功率才有意义，不能直接相加各轨的安培数来预测输入电流。PDU 读数还可能包含 CPU、风扇等，有条件时应说明读的是哪条线、什么窗口。

平均值之外是瞬态。很多计算块一起从等待进入算术阶段，电流斜率 di/dt 有可能陡增；去耦电容先补电，稳压回路随后跟上。简化来看，有电阻性的 I·R 压降、电感性的 L·di/dt 项，也有电容放电：补电之前，缺掉的电荷约为 ∫ΔI dt，电压变化约为该电荷除以有效 C。实际电源分配网络（PDN）要看频域阻抗：小信号近似下，电流扰动在某一频率上的分量乘以该频率的阻抗，决定对应电压扰动幅度。相同 ΔI 的两条波形，如果频谱不同，引起的最深电压下陷也可能不同。

| 时间尺度（示意） | 要解决的问题 | 合适的验证方式 |
|:--|:--|:--|
| 芯片/封装的 ns–µs 瞬态 | 哪些区域同步开工会引发 droop？时序余量够不够？ | 平台批准的片上检测器或专用轨级高速探测，结合 PDN 模型 |
| kernel/设备的 µs–s 活动 | 哪个阶段变忙、触发限功率，或改变 J/token？ | 对齐 kernel markers、板级电能和计数器；传感器够慢时用重复受控实验 |
| 服务器/机柜的 ms–秒级及更慢变化 | 多卡是否同步起落？供电、散热如何规划？ | 同步的模块/服务器/PDU 功率时间序列，按所关心窗口计算峰值和爬坡 |

这里最容易出现证据越界。[HPCA 2026](https://lca.ece.utexas.edu/pubs/jiang_hpca26.pdf)同时有 A100 上的设备遥测阶段变化，以及基于模拟的 MHz 内核功率波动与 PDN 下陷分析。**MHz 波形和 SPICE 得到的下陷量不能当作 A100 供电轨示波实测。** 反过来，板卡的 10 ms 或 100 ms 功率读数看不到突变，也不能证明芯片上没有更快的尖峰。集群则是另一个尺度：很多 rank 同时退出 PP 气泡、结束屏障或切换 RL 阶段，可能叠成更陡的机柜功率变化；不能用单卡平均值或芯片 PDN 模型去替代机柜端测量。

## 第五课：怎么设计一套 GPU/NPU 都能做的实验？

**先校准仪器，再解释 workload。** [SC24 研究，§5.1 和图 17](https://arxiv.org/html/2312.02741v3#S5)发现，部分受测 A100/H100 的瞬时功率字段存在约 25 ms 观测窗与约 100 ms 更新节奏。在指定 A100 上，用 100 ms 周期负载时，能量误差的标准差可到约 30%；有控制地改变重复任务与采样窗的相位，将其降至 5% 以下。这里说的是**该实验误差的离散程度**，不是仪表统一保证 ±5%。把 API 从每 100 ms 轮询改成每 5 ms，既不能改变传感器观察窗口，也不能补回缺失波形。

建议先做一张最小矩阵，再跑真实模型：

1. **空闲 → 矩阵 → HBM → 互联。** 先稳定温度并记录频率与功率限制，测空闲。矩阵组固定形状、精度和实际 kernel，比较全零、随机和有代表性的模型数据；访存组比较 L2 能容纳与明显超出 L2、读与写；通信组分别记录是否跨节点、各 rank 方向字节和等待。
2. **串行与重叠做成一对。** 同样数量的 GEMM 和通信，比较串行与通算重叠，验证完成的工作和实际执行率。若环境和完成速率可比，可用 `P_overlap − P_compute − P_comm + P_idle` 看非加性残差；不满足条件就只报整体能量和吞吐差，不能把残差说成某个物理模块功率。
3. **最后跑实际 train / prefill / decode。** train 标注 forward、backward、梯度通信和 optimizer；有 RL 分池时分开汇报 rollout、训练和权重同步，并在同一作业窗口汇总能量。推理扫 batch、输入长度、输出长度和请求到达模式，记录 TTFT、TPOT、吞吐和有效输出 token。对 MoE，记录最慢 rank，不要只看八张卡的均值。
4. **用同一时间轴出报告。** 设备与外部功率表尽量同步；记录采样字段、实际更新时间、平均窗以及查询开销。先做长稳态，再做多周期、相位错开的重复实验；需要真实波形时另采不改变相位的原负载。至少报告平均瓦数、给定窗口的 p95/峰值与 ramp、全设备 J/有效 token，以及同窗口的频率和带宽。重复几轮并报告离散程度；无轨级探测就不要填“核心峰值 A”。

Ascend 侧可以用 [MindStudio msMonitor](https://mindstudio-docs-master.readthedocs.io/zh-cn/latest/msmonitor-whl/docs/zh/advanced_features/monitor_feature/)对齐 Kernel、Communication、Marker 与 DCMI 设备/AICore/HBM 指标；文档给出的采集间隔是软件配置，**设备功率 W 不是核心轨 A，HBM 利用率百分比也不是已测得的读写字节**。要分析 HBM 与互联电流来源，还得核对平台支持的计数器和外部测点。本文没有可比的昇腾 950 核心轨公开实测，GPU 案例的安培、功率比例和 droop 数字不应移植过去。

**课后题：两个训练作业的平均功率一样，能否共用一份供电结论？** 不能直接共用。先核对做完同样工作各要多久，决定能量；再看同一电源轨的峰值和斜率，决定局部瞬态；最后看相邻卡和机柜的波形是否同相，决定集群电力预算。**从 FinFET 到集群，因果链一直是：器件提供开关，负载安排电路活动，供电网络把活动变成不同尺度上的电流和电压波形。**
