资料截至北京时间 2026 年 11 月 23 日 05:30。两项修复分别于北京时间 11 月 22 日 14:20 和 18:17 合入 vLLM 主线，下文以相应合入代码及 PR 公布的实验为准，不等于某个已发版镜像已经包含它们。

推理服务有一个容易误判的现象：**CPU 或磁盘都存了不少 KV，但用户返回时，首 token 还是在等长 prompt 重算。** 对标准前缀查找来说，起点不是“我总共找到了多少块”，而是“从请求开头，能连续用到第几块”。假设第 1、2、4、5 块都还在，而第 3 块缺失，正常前缀查找不能直接把后面两块也算入命中。另一种情况更隐蔽：二级存储虽够大，但传输路径必须经过 CPU staging，而 staging 拒绝了一次超额申请，结果一个块也没落进去。

这两个故障分别发生在**写入**和**保留**，不宜拿一个总命中率解释。

## 1. CPU 只容得下 13 块，为什么磁盘原来一块也收不到？

[vLLM #66719](https://github.com/vllm-project/vllm/pull/66719)修复的旧路径会把运行中请求尚未存储的块一次交给 CPU manager。如果待写新块超过可用槽位加上可驱逐槽位，整个申请被拒；负责下次从哪里接着存的游标不前进。同一超额申请到了下一步又原样重试。加大后端磁盘空间治不了这个逻辑。

合入后的策略是**先收能容纳的较早 token 块**。管理器报告留待重试的后缀；上层只将各组游标前移到第一个未接收块，下个调度步再提议剩余块。已经驻留且作为本次 offer 一部分的块不能当作可用空间；CPU→二级存储的推进也不能把待重试键又算作这轮已接收。对多组 KV 分块，既要按 token 位置裁剪，也要保留 GPU 块映射顺序，不能按散列值重新排序。这里的改变不包含二级缓存回迁至 CPU 的 `prepare_write()`。

作者用 RTX PRO 6000 Blackwell、Qwen3-0.6B、单个 **7,663 token** prompt 和 64 token 的块做了验证。13 块容量的 CPU 层后接 filesystem，旧基线没有写下任何块，修复后的运行以 **10 次传输写出 119 个完整块**，报告约 873 MB。119 × 64 = **7,616 token**，剩余 47 token 不在这 119 个完整块中。验证读回时，作者**重启并换成 2 GB CPU 层**才得到 7,616 个命中 token。写入端小 staging 可工作，不等同于同一小 staging 配置已经验证了完整读回。

这也不是逐 token 正确性实验的全胜：大 CPU 一次写和小 CPU 分批写生成的文件哈希相同，但缓存恢复与全 fresh 的贪心输出在约 90 个 token 后出现分歧。哈希比对支持分批写没有改变该对照中的文件字节；它不证明两条推理执行路径逐 token 相同。基线是早于另一次代码改动的 main，不能把整套端到端差异解释成严格的同版本单变量 A/B。

还有两个上限。请求提前结束或进入单次 handoff，没有后续调度机会，那么一次尝试仍可能只存下前面一段。没有二级层时，继续写后缀甚至可能挤掉自己的早期块：此时 “store 成功” 并不意味着“可恢复前缀变长”。

## 2. 复用过的前缀，为什么可能比刚写的尾部更早被逐出？

[vLLM #69110](https://github.com/vllm-project/vllm/pull/69110)针对 ARC 策略下的另一条路径。一个正在生成的请求可能重用了已驻留的早期块，又新增了后缀。在旧实现里，运行请求的尾优先驱逐顺序会跟踪新插入的块，却没把复用的前缀块放进该请求的排序。一次加载完成后，后续存储压力就可能优先驱逐前缀，留下本次查找无法利用的后缀。

修复把**仍驻留在 ARC T1、位置已知的复用键**登记到运行请求的排序；已有归属不随另一个请求访问而转移，完成请求时才做的频率晋升逻辑也不变。这不是把前缀永久锁住，更不会补回已经被完整驱逐的请求。资源紧张时应先保哪段，这比“能不能绝对禁止驱逐”更重要。

作者在 GB10 上用 SmolLM2-135M-Instruct、240 MiB CPU KV、2 GiB GPU KV，安排四个错开的 3,073 token 请求，并只重置 GPU prefix cache 来迫使读 CPU。三个交替配对中，重放命中由 **0 到 1,664 token**，单 token 重放请求的中位延迟 **268.3 → 133.9 ms**；生成 token 与 logprob 在这些对照里一致，而并发生成时间的中位数约 **2.856 → 2.868 s**。这是由“是否能用前缀”改变的重放延迟，**不是稳态 decode 吞吐加倍**，也不能与磁盘试验叠乘出一个整体加速比。

## 3. 两个实验改变的是哪一段路径？

| 实验 | 直接观察 | 尚未证明 |
|---|---|---|
| 长 prompt、小 CPU、filesystem 二级层 | 增量落盘 0 → 119 完整块；另以大 CPU 层验证读回 7,616 token | 同一小层配置的整段读回、生产负载命中率或逐 token 等价 |
| GB10 上 ARC 并发驱逐 | 强制 CPU replay 的连续命中 0 → 1,664 token；单 token 重放约减半 | decode 加速、所有驱逐负载均受益或生产精度结论 |

对容量规划，可用一个简单的**理想下界**。若一个请求要新写 B 个完整块，单次最多 H 个、每轮都能及时腾出 staging，则至少要 ceil(B/H) 轮；119 和 13 对应至少 10 轮。对真实服务，还要看二级层可持续写入速率、每轮实际可驱逐空间、后台队列、请求结束时点及新请求竞争。给磁盘加容量，只有在 CPU staging 真能把块交出去时才有价值；给 CPU 加容量，也不保证替换策略会留下最有用的连续部分。

## 4. 验收时不要只盯“落盘 GB”

建议为同一个请求或回放样本记录四个不同的量：

1. **写多少：** 提议的完整块数、接收块、留待重试块、实际传输与后端写成块。修复后 `kv_offload_cpu_allocation_size` 记录的是裁剪后分配大小，不能直接和旧口径比较曲线。
2. **留多少：** 各层仍有多少块，以及在真实可达的查找路径上，开头连续保住了多少 token。结合前缀复用热度与分层路径，报告尾部分位数，而不是只有一个平均命中率。
3. **读多少：** 分别测试清 GPU 后读 CPU、从磁盘启动后读回 GPU、纯 cold 三条路径；同配置比较 TTFT、读回字节和额外 prefill token。结束过早、后端阻塞和完全驱逐要有单独样本。不同资源配置的结果分列。
4. **结果有没有变：** 对固定输入比生成、logprob 和完成原因；不期望跨算法逐位相同的场景要预先规定容差，不能用“文件哈希没变”替代推理验收。

如果要验证命中的 KV 能否被后续计算正确使用，可接着看[vLLM-Ascend 的 KV 缓存正确性检查]({{ '/2026/11/26/ascend-kv-hit-correctness-gates/' | relative_url }})。其中分别检查了 AscendStore 的恢复位置、Mooncake 的分段布局和各 PCP rank 的回放计划。

这补上了[此前的 Agent KV 回放分析]({{ '/2026/11/21/agent-trace-sizing-kv-restore/' | relative_url }})中的一个具体环节：缓存有多大、能落盘多少只是资源账；**能够恢复多少连续、有用且通过验证的前缀，才是服务账。**
