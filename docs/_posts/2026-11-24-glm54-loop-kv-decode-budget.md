**GLM-5.4 把中间 28 层再跑一遍，但没有为第二遍保存完整的长上下文 KV，也没有重跑一遍稀疏索引器。** 它用第一遍的稀疏历史看远处，再用第二遍最近 128 个位置的新状态修正眼前。这让增加执行深度不必同比增加权重存储和 KV 容量；是否更快，要另算每 token 成本和完成任务所需的 token 数。

智谱于 11 月 23 日发布[官方技术说明](https://z.ai/blog/glm-5.4)。本文资料复核截至 **北京时间 11 月 24 日 05:32**。架构细节来自该文的公开图和正文，性能推导均来自文中数据，不是本文实测。

## 入口已经开放，不等于权重和通用 API 已开放

[产品文档](https://docs.z.ai/guides/llm/glm-5.4.md)列出视频、图片、文本和文件输入，**输出为文本**，上下文 1M、最大输出 128K。视频、3D 和机械设计示例是用代码或工具完成任务的展示，不是模型能直接生成视频流或原生 CAD 文件的规格。上下文上限与最大输出是不同限制，也不应直接加成一条 1.128M 请求保证。

文档确认所有 Coding Plan 用户可用，周配额套餐的 GLM-5.4 配额为 GLM-5.3 的 1.5 倍；**通用 Model API 仍待安全评估完成**。发布文还列出 ZCode 和 Chat 入口。权重开放属于厂商后续计划；截至核验，[官方 GLM-5 GitHub 下载表](https://github.com/zai-org/GLM-5#download-model)未列 GLM-5.4 权重，不能据此宣称可下载部署。1.5 倍是产品配额策略，不是硬件吞吐或单位成本测量。

## 一、78 → 106，数的是层被调用几次

官方将旗舰这一部分描述为 **750B 规模**，并说明它由已预训练基座继续训练而来，并非从头训练循环模型。博客列出 1B、4B、30B、750B 的逐级验证，但没有给出每个尺度的完整等算力曲线。

官方架构图把骨干网络划为前奏 L1–26、循环 L27–54、尾段 L55–78。中段两次用同一套参数，所以独立编号层位仍是 78，单 token 前向经过的层调用次数是 `26 + 2 × 28 + 24 = 106`，按层调用次数多约 **35.9%**。图还画出由 24 层 ViT 投影到输入侧的视觉特征；它不计入上述文本骨干层数。

![GLM-5.4 两遍共享中间层及第二遍的两路 KV]({{ '/assets/glm54-two-pass-kv.svg' | relative_url }})

这个计数不是 FLOPs 倍率，更不是显存或延迟倍率。第二遍跳过索引计算，注意力读的是混合缓存；单层形状、共享资源和内核实现会影响真实代价。同一权重参与两次计算，也不保证 HBM 只读一次。若某处有基于隐藏状态的专家路由，两遍的专家选择、聚合成批和通信量也未必相同，这些需要用实际 trace 验证。

两轮分别用各自的 per-token 门控把更新写回残差，形式是 `x_new = x_old + β × (candidate − x_old)`。门值由本轮输入经 RMSNorm、线性投影和 sigmoid 生成。这是**调整每个 token 本轮改多少**，不是已经按难度动态选择循环次数。官方将可变循环深度留作后续方向。

## 二、为什么第二遍仍要读两路 KV

[架构图](https://z.ai/blog/glm-5.4)给出的逻辑是：

1. **不再算索引。** 图中最前两个层位单独设索引器，其后按四层组共享索引；循环第二遍复用第一遍生成的稀疏位置集合，不再运行自身索引器。
2. **历史与本地状态没有合并成同一份。** 第二遍从第一遍的全局稀疏历史中读所选位置（图示 top-2048），同时读第二遍自己新生成的最近 128 个位置的 KV。相同位置可以出现在两路，但代表不同轮次的隐藏状态，不宜以位置 ID 直接去重。
3. **一次联合归一化。** 两路分数属于同一次 sparse MLA 的同一个 softmax。若分别算两次独立 softmax 再平均，通常不是同一个结果。工程上可以用分块归约实现共同的归一化，但官方图没有说明生产 kernel 采用何种存储或融合方式。

把**存多少**和**每个 query 读多少**分开。若上下文为 `L`，每循环层每位置第二遍 KV 的净 payload 为 `b` 字节，而且 28 层同宽，则第二遍局部历史对应约 `28 × min(L, 128) × b`；等宽等精度的假想全长第二遍缓存对应 `28 × L × b`。以 `L = 1,048,576` 做示例，两者逻辑槽位比为 **1/8,192**。这个比只比较**新增第二遍历史**，不是模型总 KV 缩小 8,192 倍；它还不计分页、跨卡复制、落地临时空间等。也不能把 `128/2048` 当成 HBM 流量增幅：有效稀疏位置数、两路布局、缓存命中、重复读取和中间归约都会改变实际字节。

## 三、少生成多少 token，才抵得过单 token 变慢？

官方给出 **30B 同参数量**的 Loop / 非 Loop 比较：同一模型架构族，采用 200K 长上下文 SFT 设置、开启 thinking；Loop 条件总训练计算约多 10%。这是 **iso-parameter，不是 iso-compute**；200K 不作为样本数或总训练 token 数解读。下表为官方结果的精简复述与本文换算，**不代表 750B 旗舰实测**。

| 任务 | 分数：基础 → Loop | 输出 token 变化 | 仅解码时，单 token 最多可变慢 |
| --- | ---: | ---: | ---: |
| AIME25 | 19.17 → 30.42 | −2.0% | 约 2.0% |
| GPQA Diamond | 47.58 → 56.26 | −11.7% | 约 13.3% |
| AA-LCR | 40.33 → 47.67 | −9.7% | 约 10.7% |
| MMLU-Pro | 71.65 → 75.05 | −14.9% | 约 17.5% |
| IFBench | 50.20 → 53.47 | −13.0% | 约 14.9% |

如果输出长度减少比例是 `r`、每 token 解码时间增加比例是 `s`，仅看解码阶段的时间比为 `(1−r)(1+s)`，不变慢要求 `s ≤ r/(1−r)`。看似相近的“输出变短”结论，AIME25 和 MMLU-Pro 给出的速度预算却差很远。若把约数直接套到旗舰，也可能反转：官方产品文档提到旗舰在一些任务上仍会长时间思考。

表里的两个模型同时变了分数和长度，因此不能把盈亏线写成**同质量**提速。更好的部署指标是达到相同成功率与工具验收条件时的每成功任务 GPU·秒，再分解排队、prefill、decode、工具等待与重试。厂商文档的高峰 70–80 token/s、非高峰至多 200 token/s 没给硬件、批量或百分位，不宜作为每 GPU/NPU 吞吐基线；“能力接近 2T–3T 参数级”也是厂商判断，不是公开同预算消融。

## 四、仿真与实测先各立三个账本

| 工程问题 | 先记什么 | 不能用什么替代 |
| --- | --- | --- |
| 两轮真实执行代价 | 每遍 GEMM、indexer、两路 KV gather/score、归约耗时；必要时记录 HBM 字节和 EP 跨卡流量 | 106/78 层调用比直接乘到延迟 |
| 容量和并发 | 主历史 KV、第二遍窗口与 workspace 分项；逐序列长度、并发及跨卡布局 | 脱离上下文长度或分页的单序列估算 |
| 用户能得到什么 | 固定硬件、精度、任务集与成功标准，比较 p95 TTFT/TPOT、任务耗时和成功任务/GPU·小时 | 厂商产品峰值 tokens/s 或周配额 |

对于仿真，至少把循环遍次、索引是否重算、两路来源、局部窗口、联合归约实现和并行拓扑放进 profile key。否则可能给第二遍套上第一遍的索引成本，也可能误把第二遍键值放进一个与上下文等长的缓冲。对硬件设计，真正值得问的是：在长上下文、高并发和不同 TP/CP/EP 下，性能卡在稀疏历史回读、局部窗口融合、专家分派，还是权重二次加载？这要靠分遍 profile，而不是靠 1M 标签推测。

GLM-5.4 证明的是一种可交付的结构方案：**复用权重加深执行，用第一遍稀疏上下文加第二遍局部状态控制增量缓存。** 公开资料还不足以给出旗舰的等质量吞吐、实际 HBM 开销或硬件排名。在这些数据出来前，最有用的读法是把参数、算子、缓存和成功任务成本拆开。
