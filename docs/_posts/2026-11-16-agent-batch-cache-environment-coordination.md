## 先说结论：别只问 GPU 忙不忙，要问整批任务什么时候结束

一个 Agent 跑得快，不代表一千个 Agent 会一起跑得快。

原因不只是模型推理慢。每条 Agent 轨迹都在反复经历“推理、调用工具、等待返回、继续推理”。在等待期间，它占着任务名额，历史缓存却可能被别人挤掉；等工具终于返回，它又可能被路由到另一台机器，从头重算长上下文。最后，多数任务已经完成，只剩少数长链拖着整批任务无法进入下一步。

蚂蚁 Ling 团队 11 月 12 日公开的技术报告，把这些问题放进一个统一目标：**缩短 batch makespan，即从整批开始到最后一个任务结束的时间。**它研究的是模型评测、合成数据和 RL rollout 等批处理工作流，不是单纯追求更低的首 token 延迟。

## 一、先换一个性能模型：Agent 是执行链，不是独立请求

普通推理压测经常把请求视为互相独立：请求来了，进入队列，生成结束，释放资源。

多轮 Agent 不是这样。第 2 次推理，要等第 1 次工具调用返回；第 3 次推理，又要等第 2 次环境操作完成。它的依赖关系可以写成：

```text
轨迹 A：推理 → 工具排队 → 工具执行 → 推理 → …… → 完成
轨迹 B：     推理 → 工具执行 → 推理 → …… → 完成
轨迹 C：          推理 → 工具排队 → …… → 完成
```

同一时刻，系统需要回答三类不同的问题：

1. **允许多少条轨迹进场？**这是样本并发，每条轨迹从进入到结束一直占一个名额。
2. **允许多少个环境操作真正运行？**这是工具执行并发，受 CPU、容器、外部 API 配额等约束。
3. **哪条已经就绪的推理请求先跑，送到哪里？**这决定负载平衡与历史缓存能否复用。

如果把这三个问题都压进一个 `concurrency`，很容易两头受限：设得小，GPU 等工具；设得大，工具过载、缓存被冲掉。

还有一个重要差别：在线聊天通常关心每个用户的等待时间；离线评测和同步 rollout 更关心整批最后一个任务什么时候结束。**平均请求延迟最小、平均任务完成时间最小、整批完成时间最小，并不是同一个优化问题。**

## 二、第一层：缓存不是越多越好，而是两种状态必须配套

Ling 使用的混合模型同时包含 Attention 与递归状态层。跨轮复用历史时，仅保住 KV cache 不够，对应递归状态也要还在。反过来，递归状态池很大而 KV 池太小，同样没用。

可以把它想成两种配套零件：每保住一条轨迹，都要一份 KV 和一份递归状态。总容量由先耗尽的那一类决定。

设扣除权重和其他运行时预留后，缓存总预算是 `M`；一条典型轨迹需要 `Fkv` 的 KV 空间和 `Fstate` 的递归状态空间。那么：

```text
可同时保留的轨迹数 ≈ min(KV 池 / Fkv，状态池 / Fstate)
两池平衡时：状态池 / KV 池 ≈ Fstate / Fkv
平衡后的参考容量 ≈ M / (Fkv + Fstate)
```

这是容量估计，不是性能定律。论文用历史轨迹最后一轮的平均上下文估计 KV 需求；它没有精确覆盖长度长尾、分配粒度、运行时碎片，也不保证等于最优并发。作用是给调参提供一个靠谱起点，而不是靠默认比例盲试。

这里还有两个容易误读的细节：

- **这是部署前的静态分池，运行过程中不动态搬移两池容量。**
- 论文采用每条轨迹保留最新可复用递归状态的方式，不是把每一轮的状态全部留下。

因此，短上下文、多轨迹的任务与长上下文、少轨迹的任务，适合的状态/KV 比例可以相差很大。配置文件里一个“全场通用”的比例，并不意味着资源使用合理。[论文 §3.1、§3.4](https://arxiv.org/html/2611.16661v1#S3)

### 一个反例：并发翻倍，整批完成反而多用 70 分钟

Ling-3.1-Flash 的 SWE-bench Multilingual 实验很直观。三种配置的硬件和模型相同，都是两个 TP8 worker，共 16 张 H20；每种配置运行三次，表中是平均值。

| 指标 | 调好并发的原始基线 | 只把并发提高的基线 | 联合优化 |
|---|---:|---:|---:|
| 样本并发 | 50 | 100 | 100 |
| 整批完成时间，分钟 | 234.1 | 304.1 | 185.1 |
| 输入 token 缓存复用率 | 98.20% | 80.41% | 98.27% |
| 新计算的 prefill，百万 token | 19.30 | 211.81 | 17.93 |
| 平均 TTFT，秒 | 2.54 | 11.81 | 5.88 |
| 平均 TPOT，毫秒/token | 24.30 | 60.84 | 36.37 |

只提高并发，缓存复用下降，新 prefill 增加到约 11 倍，整批多用了 70 分钟。联合调整缓存比例、排队策略与路由以后，同样 100 并发，整批时间相对高并发基线缩短 39.1%。

但如果与原来的 50 并发基线比较，优化后整批虽然快了 20.9%，单请求 TTFT 和 TPOT 仍然更高。**这不是实验自相矛盾，而是用更多同时在途的工作，换取整批更早结束。**对于有严格在线延迟 SLO 的服务，不能直接搬用这个工作点。[论文表 2、附录 A.3](https://arxiv.org/html/2611.16661v1#A1.SS3)

## 三、第二层：缓存留住了，还要让下一轮找得到、用得上

### 1. 跨 worker：尽量回老地方，但别死守一台机器

论文的 LBCH 路由给每条轨迹一个稳定标签，再通过一致性哈希确定“常驻 worker”。下一轮尽量回到原处，复用已有历史。

问题在于：固定绑定会造成热点。有的轨迹长、有的短，有的工具很快返回、有的很慢，即使初始分配均匀，运行中的队列也会失衡。

LBCH 因此增加负载上限：如果常驻 worker 的排队加执行请求数超过允许范围，就沿哈希环寻找合格的其他 worker。它用当前请求数控制倾斜，不要求检查完整 prompt，也不需要预测剩余生成长度。

这里的取舍是真实存在的：改派当前请求可能损失缓存，留在原 worker 可能等更久。该论文选择**worker 本地缓存复用，不做跨 worker 缓存迁移**。所以它不是一个全局 KV 传输方案。

### 2. worker 内：到了老地方，也可能排到缓存过期

路由亲和性只回答“去哪里”，不回答“什么时候跑”。请求在本地队列里等太久，对应缓存仍可能被挤掉。

RP 调度先记录近期服务过的轨迹标签，然后优先考虑这些轨迹的后续请求；对这部分候选再查询真实前缀命中长度，优先复用较长前缀。其他请求仍在队列中等待，随后由已有 batch builder 按资源约束接纳。

这个设计不仅节约重算，也节约调度器自身的工作：如果每轮都对整个长队列做长前缀匹配、遍历缓存树，CPU 开销可能很可观。RP 用标签筛选，再复用已经算过的命中长度，减少重复查询。

不过，**近期标签表不等于缓存驻留表。**标签还在，KV 可能已经被淘汰；标签被移出，KV 也可能仍在。已记录的命中长度还可能变旧。论文明确承认这些近似，不能把 RP 描述为“精确知道所有缓存位置”的调度器。[论文 §3.2–3.3](https://arxiv.org/html/2611.16661v1#S3.SS2)

本站此前的 [SGLang 会话路由解读]({{ '/2026/11/13/sglang-session-routing-cache/' | relative_url }})讨论了“入口引擎与内部缓存域不一致”的问题。这里进一步说明：即使路由域已经对齐，缓存容量和本地等待顺序仍然会影响实际复用。两篇不是同一个补丁，也不能把论文效果归给那个路由提案。

## 四、第三层：工具只能跑三个，不等于只能接纳三条 Agent

假设外部服务只能承受 3 个同时运行的工具任务。

一种直觉做法是把 Agent 并发也设成 3。但这三条轨迹可能一起等工具，此时 GPU 就没有新工作。等待工具的轨迹占着任务名额，却没有利用推理资源。

论文把两道门拆开：可以接纳更多活跃轨迹，但工具执行仍严格限制为 3。这样，一部分轨迹执行工具时，另一部分轨迹继续推理；工具额度没有增加，只是不同阶段更好地重叠了。

```text
样本入口：最多 50 条活跃轨迹
             ↓
       推理就绪队列 → GPU
             ↓
       工具等待队列 → 3 个执行槽
             ↓
        返回对应轨迹，继续推理
```

这也不是并发越大越好。工具释放后继推理的速度有上限，多接纳的样本最终只会堆积在工具队列里，同时挤占缓存。论文的回放实验里，从受限统一入口提高到 10 条活跃轨迹就有明显收益，整批时间约缩短三分之一；再到 25、50，改善开始趋平。

**分析判断：样本准入应该由两侧共同决定，但不应该简单等于两侧执行容量中的较小值。**关键要看阶段交替比例、工具等待时间、缓存驻留预算和可接受排队，而不是复制一个并发数字。

## 五、第四层：队列里先放谁，决定谁会在最后拖住全场

容量拆开后，工具等待队列可能更长。此时 FCFS 按先来后到处理，并不一定能最早完成整批。

论文的 CAAS 可以直观理解为：**在相近时间到达的任务中，优先推进已经走得更深的执行链，让它们后续还有多少工作尽早暴露出来。**

它没有预言未来的总轮数，而使用四级排序：

1. 先保护较早到达的时间组，避免新来的深链反复插队。
2. 同组内，已完成推理轮数更多的轨迹优先。
3. 同深度，再用历史平均推理时长的粗粒度分桶打破平局。
4. 仍然相同则按入队先后。

论文使用 30 秒到达分组、1 秒推理时长分桶。这些是该实验的参数，不是通用最优值。

需要强调：CAAS 改变工具任务的**发出顺序**，不加工具执行槽，不缩短单次工具服务时间，也不修改 Agent 的动作。它试图避免“长链直到大多数短任务结束后，才慢慢暴露自己的后半段”。但已走得深不等于一定还剩得多，所以这是启发式，不是最优 makespan 的保证。[论文 §4](https://arxiv.org/html/2611.16661v1#S4)

## 六、最大的 65% 收益，到底来自哪一层？

不能把整套方案的收益全部归给 CAAS。论文在真实 MCP-Atlas 执行中给了一个很重要的拆分：

| 模型 | 统一入口原始基线 | 推理优化 + 分离入口，工具 FCFS | 进一步改用 CAAS |
|---|---:|---:|---:|
| Ling-3.0-Flash | 466.1 分钟 | 168.2 分钟 | 163.0 分钟 |
| Ling-3.1-Flash | 333.5 分钟 | 140.5 分钟 | 128.5 分钟 |

每种配置为三次 500 任务运行的均值；同一模型内硬件固定，工具容量均为 3。原始样本并发为 3，两种优化配置为 50。

第一步已经带来 63.9% 和 57.9% 的下降，包含推理侧优化与入口解耦两部分。第二步从 Opt-FCFS 换成 Opt-CAAS，额外下降才是 3.1% 和 8.5%。如果拿 466.1→163.0，称作“CAAS 加速 65%”，就是把不同实验层次混在一起了。

还要分清回放与真实执行：回放固定记录的环境响应和时长，适合比较策略本身；真实执行会遇到生成随机性、外部环境变化、失败与重试。作者的真实运行总时间包含这些失败和重试，没有只留下成功样本。报告里的任务得分总体接近，但三次运行的均值不能证明质量严格等价。但用于部分回放的历史轨迹只收集了成功执行，因此回放不能证明完整失败分布下的鲁棒性。[论文 §5.3–5.4、附录 A](https://arxiv.org/html/2611.16661v1#S5.SS3)

### 更早结束，最后 5% 为什么反而更久？

Ling-3.1 的原始基线最后 5% 用了 26.1 分钟，Opt-CAAS 是 35.3 分钟。只看这个数字，会误以为优化把尾巴搞坏了。但整批实际从 333.5 分钟缩到 128.5 分钟。

原因是两次“最后 5%”不再是同一组任务。入口很窄时，最后结束的可能只是最后才获准进入的普通任务；入口放开后，短任务早就跑完，真正长的轨迹集中留在末尾。论文还按任务 ID 对照了这些尾部任务的轮数，支持这一解释。

因此，比较不同准入策略时，至少应同时看完整完成曲线、整批终点，以及按相同任务 ID 对齐的完成时间。**尾部区间长度不是一个脱离样本组成仍然可比的万能指标。**

## 七、对训练和推理系统设计，真正有用的启示

以下是基于论文机制的工程分析，不是作者已经验证的额外结论。

### 1. 把“缓存驻留预算”变成准入控制的一等输入

只有 HBM 已用量还不够。需要知道活跃轨迹数、它们的上下文长度分布、两类状态池的压力，以及新 prefill 量。高并发后 GPU 忙起来，可能是在重算，不是在更快地产生有效数据。

建议沿并发扫描同时画两条曲线：整批 makespan 与新 prefill token。若并发增加后后者陡升、前者反弹，应先查缓存抖动，而不是继续加请求。

### 2. 工具资源和 GPU 资源要有独立计量

不要把“任务活跃”当作“正在用 GPU”，也不要把“等待工具”当作“占用了工具执行槽”。日志应把 admission、推理排队、推理执行、工具排队、工具执行分开，否则扩容决策可能完全找错瓶颈。

### 3. RL 应再加一条模型质量与版本约束

如果 rollout 必须整批齐备才开始更新，makespan 的缩短有直接价值；若系统已经异步消费样本，还要看样本年龄、策略版本偏差与有效训练样本吞吐。本文不是异步 RL 收敛实验，也没有证明训练达到同等奖励所需时间减少了同样比例。

### 4. 不要把离线最优点当成在线默认值

论文已经展示：整批更快时，单请求 TTFT 可能更慢。在线 Agent 服务必须加上用户等待预算、超时和公平性约束；对回访轨迹优先，也要检查新任务是否等太久。

### 5. 需要补上的验证，不是再报一个峰值加速比

真正值得后续跟进的是：负载分布改变后静态分池是否仍然合适；长工具等待与缓存淘汰如何联动；异构工具槽位能否继续使用同一排序；策略对失败、重试和长期公平性有什么影响；实现发布后能否在其他混合模型上复现。

## 总结：Agent 系统的优化单位，正在从 token 变成执行链

这篇报告最有价值的地方，不是某个单独的调度名字，而是把五件事连起来：**缓存怎么分、样本进多少、下一轮送哪里、队列谁先跑、工具先释放哪条链。**

局部指标依然重要，但要服务于整体目标。少一次 prefill 重算、提前一次长链工具调用，可能比多塞几个请求进 GPU 更有效。反过来，一个看似漂亮的缓存命中率或尾部百分位，也可能掩盖错误的对照组。

要判断 Agent 系统是否真的更快，最后仍要回到同一个问题：在相同资源与质量要求下，这批工作究竟什么时候能交付？
