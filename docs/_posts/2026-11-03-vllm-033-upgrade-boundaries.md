## 依据版本与阅读结论

本文依据 vLLM 于 **2026 年 11 月 2 日 10:10:05 UTC**（北京时间 18:10:05）公开的 [v0.33.0 发布记录](https://github.com/vllm-project/vllm/releases/tag/v0.33.0rc3)及关联 PR，属于北京时间 11 月 3 日 07:30 截止的最近 24 小时发布窗口。关联 PR 的合入时间更早；本文解读的是本次版本汇总，而非把旧 PR 当成当天新事件。

核验时，发布名称为 `v0.33.0`、`prerelease=false`，但记录仍挂在 `v0.33.0rc3` 标签下。安装产物版本、发布名称和源码标签需分别核对，不能仅凭 URL 后缀判断发布状态。本文没有独立运行性能或兼容性测试。

**结论：这不是一组可以无条件叠加的加速开关。** 构建产物、采样语义和分布式依赖分别改变了不同边界，应该分开验收。

## 1. CUDA 13 并非新默认，变化是停止额外 cu129 产物

[PR #62575](https://github.com/vllm-project/vllm/pull/62575)明确指出：CUDA 13.0 此前已经是默认变体，本次从发布流水线删除的是 CUDA 12.9 的额外 wheel、镜像和多架构清单步骤。因而，“vLLM 本次首次迁移到 CUDA 13”是不准确的概括。

对依赖 `-cu129` 或 `-cu129-ubuntu2404` 标签的团队，影响首先发生在**新版本交付路径**：不能继续假定同名变体随版本更新。它也不等于历史产物已删除，或所有 CUDA 12 环境在理论上都不可能编译运行；后两种断言并不是该 PR 证明的内容。

PR 还提醒，相关预编译 wheel 自动选择逻辑与安装文档存在后续工作。由于本文未验证所有后续修复，不能据此断言读者当前安装路径必然成功或失败。

**工程判断。** 先盘点生产实际使用的镜像摘要、驱动、GPU、Python 环境与扩展，再建立新版本的独立验证环境。保留已验证旧产物作为回退点，不要让滚动标签隐式替代固定版本。构建选择正确只是第一关，启动成功也不代表算子与业务路径全部兼容。

## 2. FLy 改变了接受规则，因此不是无损推测解码的同义词

标准推测验证会在首个拒绝位置停止接受后续草稿。按 [PR #53987](https://github.com/vllm-project/vllm/pull/53987)的实现说明，FLy 在目标分布的熵满足门槛、且接下来一个完整窗口的草稿都通过原生验证时，可以容忍一个孤立的拒绝位置。它不要求额外的目标模型前向，但改变了 token 接受决策。

这是 **opt-in、刻意有损** 的策略，标准验证仍是默认。它不保持目标分布，也没有普遍的准确率下界。代码中的熵门控采用处理后分数的 top-k 概率，而不是直接照搬论文中的全词表归一化熵；理解实现时应以实际版本为准。

PR 报告的 MRV2 测试覆盖四个模型、MI355X 与 B300、多档 batch size，吞吐提升随配置变化。这里不把其中的最好值写成全体用户可得的收益。质量评测是单次 pass@1，部分题集很小，并包含退化；作者也注明部分模型评测没有在最新 rebase 与索引宽度修复之后重跑。

**工程判断。** FLy 应作为单独实验变量，而非在升级时顺手打开的默认优化。对照至少应包含目标模型直接生成、标准推测解码和 FLy 三组，并固定模型、提示、采样参数、停止条件和并发。除了输出 token/s，还要看业务正确率、长输出一致性、结构化结果有效率与尾延迟。

如果场景要求保持目标采样分布，FLy 的设计边界本身就是排除理由；如果允许质量—速度权衡，也应先确定业务容忍度，不能把小样本“接近基线”理解为质量保证。上述验收建议是本文分析，不是项目官方认证流程。

## 3. NIXL 1.5：压缩描述符改善控制开销，但不是传输带宽翻倍

[PR #61032](https://github.com/vllm-project/vllm/pull/61032)把逐块 KV 描述符改为 NIXL 1.5 支持的跨步列表。一行描述一组规则间隔的数据块，减少启动与握手时在 Python/NumPy 和 NIXL 之间构造、复制大量描述符的开销。实际请求仍使用同样的平坦块索引；PR 明确说传输路径没有改变。

这解释了为什么收益不能直接宣传成“稳态推理同比例加速”。作者在单个 GB300 节点、Qwen3-8B、NIXL 1.5.0 的 P/D 测试中，报告 prefill TP2 → decode TP1 场景的冷首请求中位时间从 2,656ms 降至 425ms，而热请求时延没有相应改善。这是指定大 KV 池与玩具代理下、三轮测试的结果，不是跨硬件、跨网络的普遍结论。

更直接的运维影响是：**该 connector 在 NIXL 低于 1.5 时拒绝启动。** 这是启用该路径的硬要求，不是“装了新库会更快”的可选建议，也不应扩大解释为每一种 vLLM 单机部署都必须使用 NIXL。

**工程判断。** P/D 分离部署要核对两端镜像、连接库与并行配置，将冷启动、首次握手和稳态传输分开测量。大 KV 池缩短控制路径，未必改善网络传输瓶颈；不要用冷请求收益预测长期吞吐。

## 上线前的最小验收表

| 边界 | 需要确认 | 不应据此推导 |
| --- | --- | --- |
| 发布产物 | 实际版本、标签、摘要及依赖组合 | 新版本一定存在 cu129 变体 |
| 输出语义 | 标准验证与 FLy 分开评测 | 吞吐提高意味着质量无损 |
| KV 连接 | 使用 NIXL connector 时满足 1.5 门槛，两端连通 | 启动优化等于稳态带宽提升 |
| 业务回归 | 冷/热路径、结构化输出、失败恢复与回退 | 少量演示通过等于生产可用 |

本次发布还涉及 PyTorch 等依赖和服务行为变化，本文聚焦上述三项，不是完整迁移清单。实际升级仍需逐项对照[完整发布说明](https://github.com/vllm-project/vllm/releases/tag/v0.33.0rc3)。最稳妥的决策依据不是版本号或单个峰值，而是目标环境下可复现、可回退的验收结果。
