四张卡一起做 MoE prefill。三个 rank 已经做完本地专家 GEMM，却不能往下走，因为第四张还在算。此时服务端看到的是“这一轮 prefill 还没结束”，但三张快卡各自已经出现了短空窗。BubbleTea 的关键想法是：**不要等整个推理迭代空闲，直接在这一层、这一张卡上安排可控的微调工作。**

[论文 v1](https://arxiv.org/abs/2611.24496)的提交记录为 11 月 18 日 14:24 UTC，列入 arXiv cs.OS 11 月 19 日公告。本篇按北京时间 11 月 20 日 05:30 的资料窗口整理，依据论文中的实验，不把结果当作部署保证。

## 一、EP 气泡和 PP 气泡长得像，成因不一样

PP 气泡来自流水线不同 stage 的依赖与微批排程。这里的气泡发生在**同一 MoE 层**：路由将 token 分给各卡的专家，先完成专家计算的 rank 要等输出汇合。服务迭代整体繁忙时，局部 rank 仍可能有空闲算力。尤其是长 prompt prefill，专家工作持续足够久，负载差才有机会形成能装下 kernel 的空窗。Decode 也可能不均衡，但这里的长空窗收益不能泛化到短 decode step。

论文用一个简洁的 tile 估计器。设 M 是 grouped GEMM 的 token tile 高度，专家 e 收到 n(e) 个 token。某 rank 的工作量近似为本地各专家的 ceil(n(e)/M) 之和，记为 tiles(g)。同组最重 rank 决定计算侧的收尾时点，于是：

```text
预计空窗(g) ≈ 单 tile 时间 × [最大 rank tile 数 − 本 rank tile 数]
```

例如一组四卡是 [20, 20, 24, 36] tiles，每 tile 假设 8 μs，那么估计空窗约 [128, 128, 96, 0] μs。若提前 60 μs 停止接新工作，前三卡接纳窗只剩 [68, 68, 36] μs，第四卡不开放。数字是示意；实际预算还受当前依赖、kernel 启动和共享资源影响。**只数每卡 token 还不够**：不同专家的 token 被分别向上取整，同样的总 token 可以产生不同 tile 数。[论文 §2–3](https://arxiv.org/html/2611.24496v1#S3)

## 二、怎么填：短任务、设备侧启动、提前关窗

BubbleTea 把 LoRA 微调图编译成目标不超过约 50 μs 的小块，把通信依赖显式化，并预排 CUDA Graph。独立微调进程经 CUDA IPC 读服务已加载的底座权重，不另装一份底座；还有 LoRA 参数、梯度、中间量和缓冲区，显存开销不等于零；论文估计 Qwen3-30B-A3B 的第二份底座本来需要约 15 GB/卡，这部分空间可留给 KV。做完专家计算后，服务流写标志打开窗口；训练流等设备侧 gate 与数据都就绪才执行。跨 GPU 依赖用设备侧 mailbox，避免每小块都往返 CPU。两条训练链可在一条等数据时让另一条前进，但 prefill 在过去一秒占比高时串行，降低带宽争用。

最重要的限制是：**已经发射的块不能靠关窗抢占**。论文在本配置用 60 μs 提前关窗、4k 以下 prefill 不做气泡填充，并禁止最重 rank 接新工作。预测器的中位误差约 8.9 μs，不能拿中位误差当尾部保证，更不能把 60 μs、4k 和 70% 三个阈值直接移植。一个 rank 没有计算任务，也可能正在做输出汇合，HBM、链路或通信 kernel 依然可能忙。[论文 §3.2–3.3](https://arxiv.org/html/2611.24496v1#S3.SS3)

## 三、把“整体快了几倍”和“气泡贡献多少”拆开

作者用同一台 4×A100-SXM4-80GB NVLink 服务器、vLLM BF16 跑 Qwen3-30B-A3B、Qwen1.5-MoE-A2.7B、DeepSeek-V2-Lite。微调量用 samples/s，服务用相对 serving-only 的 p90 TTFT 和 p90 TPOT。受控负载是长 prompt、32 个输出 token；另外回放两段各 10 分钟的 Azure 生产到达轨迹，不等于接入真实生产流量。

| 对照 | 论文结果 | 可用于回答什么 |
|:--|:--|:--|
| 完整 BubbleTea 对 LLMStation，三个模型 | 微调吞吐 1.9–6.2×；63 组中 50 组的两项 p90 均不超过独占服务 +10%，LLMStation 为 44 组 | 完整系统收益；含细粒度编译和调度，不能全给 EP 气泡 |
| 完整方案，对只用 decode/空闲窗口的细粒度 Tea，Qwen3 8k | 中/高负载 +24%/+27%，低负载 −3% | 尽量隔离 prefill 气泡的边际贡献；低负载不必开 |
| 打开 EPLB，Qwen3-30B-A3B，16 个冗余专家 | 作者报告 prefill 气泡占比 11–17%→8–13%；高负载填气泡比 Tea 多 12–23% 微调吞吐 | 均衡专家和回收残余空窗可兼容；8–13% 不是整机长期闲置率 |
| 两条短周期到达轨迹回放 | 对 LLMStation 微调吞吐 3.2–3.3×；两项 p90 在独占服务 +7% 内 | 支持这些回放场景；没有给生产级长期 SLO 保证 |

对照版本也有代价：作者为当前 vLLM/PyTorch 移植 LLMStation，原融合路径不支持所测试的 EP MoE，因此用单独 PyTorch/MPS 路径、选其测试中较快的专家 GEMM；无协调基线是 stock LoRA + MPS，限制 40% SM 份额。它们是明示的、可讨论的基线，不是最强可能的生产实现。[论文 §4](https://arxiv.org/html/2611.24496v1#S4)

**负例比峰值更能指导部署。** 4k 高负载的消融中，无约束填充把微调从 Tea 的 0.73 提到 2.11 samples/s，却把 p90 TTFT 拉到独占服务的 5.03×；完整策略退到 1.00 samples/s，把 p90 TTFT / TPOT 控在 1.01× / 1.04×。另一个开启 EPLB 的中负载点，16k、1 req/s 下 p90 TPOT 为 1.32×，说明即使同一套防护也有失手的时候。真正的目标是固定服务 SLO 下做更多微调，而不是把空窗填得最满。[论文 §4.4–4.5](https://arxiv.org/html/2611.24496v1#S4.SS4)

## 四、移植到超节点之前，先验三个假设

1. **先还原关键路径。** 每层每 rank 同时记录有效 token、实际 expert tile、dispatch/combine 开始与结束、HBM 字节和链路流量。复算最重 rank，画出 p50/p95 窗口和预测失误尾部。单机 TP/EP 的输出汇合不代表跨机 EP All-to-All；不能把等待通信的整段都判作可用。
2. **先做 Tea，再开启 BubbleTea。** 在同一个模型、kernel、并行拓扑与到达序列下跑 serving-only、只填 decode/空闲、再填 prefill 三档，并对照 EPLB 和拥塞压力。额外报告 p99 TTFT/TPOT、SLO goodput、微调吞吐、HBM 余量、通信尾部和 rank 级超窗率。策略要能在预测变坏、互联变忙或服务逼近饱和时自动撤掉微调。
3. **算两笔资源账。** 论文没有能耗、换代硬件或全参训练验证。本方案验证的是共用冻结底座的 LoRA 共置；不能拿来承诺 RL 权重更新、优化器状态同步或跨节点带宽免费。在给定服务质量下，另测填窗前后板卡/模组 J、单位微调样本增量能量，以及峰值功率和相邻卡电力变化。编译能拆开的最短有效块、对通信完成的观测、跨流隔离，都是设备和运行时需要实测的能力。

我的判断：**先优化慢 rank，再定价剩余气泡。** 很多时候收紧最慢 rank 的真实关键路径比填空更能改善服务；长 prefill、大负载且已经做过均衡时，再用可撤回的后台微调把剩余价值拿回来。BubbleTea 最有价值的贡献不是一个 6 倍数字，而是把调度依据从整卡平均利用率推进到“每层、每 rank、在下一条依赖前还有多少安全时间”。
