**公开 Agent 轨迹可以帮助调出第一套参数，但不能直接决定给业务配多少卡。** Gretz 等在 llm-d 上部署四个 MoE 模型时，用目标模型采集的轨迹回放，达到的最佳并发约为公开轨迹的一半，每 GPU 吞吐约为六成。另一个独立的覆盖实验中，24 次跑测都没有触发 CPU→GPU 的 KV 回读，尽管持续负载已经触发了 GPU→CPU offload。两件事指向同一问题：**请求量压上去了，不等于关键状态也压出来了。**

本次资料核验截至北京时间 2026 年 11 月 21 日 05:32。本文依据 [arXiv:2611.25905v1](https://arxiv.org/html/2611.25905v1)。v1 [提交史](https://arxiv.org/abs/2611.25905v1)记为 11 月 19 日 10:54:57 UTC；该条目进入 arXiv [11 月 20 日 cs.AI 列表](https://arxiv.org/list/cs.AI/recent)。按[官方排期](https://info.arxiv.org/help/availability.html)对应美国东部周四 20:00 的公告批次，即北京时间 11 月 20 日 09:00。这是按批次折算的公开时间，不是提交时间。

## 一、最佳并发少一半、每卡吞吐少四成，不能混成一个折扣

论文 [§8](https://arxiv.org/html/2611.25905v1#S8) 报告了 GLM-5.3、Nemotron 3 Ultra、DeepSeek-V4.1-Flash-1017 和 Kimi-K3 在 H100/H200 上的上线准备。第一轮用公开形状轨迹做初调：H100 上用 WEKA，H200 上用 Moontrace，以 AIPerf 回放，逐档提高并发。第二轮用真实 agent 在目标模型上跑代表任务，记录全内容轨迹，再用 Inference Perf 的 OTel 回放压上并发。后者的最高未退化负载档位约为前者一半，每卡吞吐约为前者 60%。

三个限定决定了数字该怎么用：

1. **一半是并发档位，六成是每卡吞吐。** 都不是生产会话成功率，也不是 H100/H200 或不同拓扑的效率比。最终引擎配置未公开，论文没有给出统一可复现的尾延迟和错误率阈值。
2. **轨迹和回放工具都变了。** 作者主要归因于业务形状和输出长度差异，这是合理解释，但不是同一 replayer 上只换轨迹的因果消融。不能把六成固化成采购折扣。
3. **线上只核了单请求长度分布。** [附录 E](https://arxiv.org/html/2611.25905v1#A5) 的 GLM-5.3 生产样本约 220 万请求、覆盖四天。目标模型采集的四类基准轨迹，在输入和输出长度上都比 WEKA 接近生产直方图，但没有任何一类单独匹配；没有生产会话依赖、前缀共享和到达时序的验证。

一个系统推论：哪怕两个 workload 的输入 token 直方图相同，**未命中、需要实际计算的 prefill token** 也可能完全不同。输出长度、工具等待和子任务依赖还会改变请求何时返回计算队列、KV 多久被重新访问。容量曲线应该对这些变量分别敏感，而不是只对平均输入长度和平均 tokens/s 敏感。

## 二、回放能稳定负载，但不替代真实 agent 的质量测试

这套回放从保存的消息及时间关系推断依赖图，保留并行分支、汇合及前驱完成后的等待，再调用目标推理端点。它把目标模型生成的响应向后传播，却使用已记录的工具返回，并可约束工具选择。也就是说，**模型是真的，工具执行不是一次新的现场运行。** [论文 §4](https://arxiv.org/html/2611.25905v1#S4)；[Inference Perf 文档](https://github.com/kubernetes-sigs/inference-perf/blob/main/docs/otel_trace_replay.md)。

| 测试（40 个会话） | 回放：总输入比 P95 | 实时重跑：总输入比 P95 | 回放：总输出比 P95 |
| --- | ---: | ---: | ---: |
| HWE-Bench / GLM-5.3 | 1.12× | 4.98× | 1.28× |

来自论文 Table 1。先对每个会话以其原始记录作分母，再取 P95；不是服务延迟 P95，不是总流量误差，也不是绝对偏差分位数。同表里 HWE-Bench 回放的输出 token 比中位数是 0.74×，所以“输入更可重复”不能写成“输出逐字复现”或“负载完全相同”。

应把三种实验留在同一套上线流程里，而不是互相取代：

| 方法 | 最适合回答 | 单独做不到 |
| --- | --- | --- |
| 真实 agent 端到端 | 新后端能否完成目标任务，工具和模型是否配合 | 每次给出相同负载 |
| 目标模型轨迹回放 | 在相近会话形状下，比较服务版本和容量 | 证明真实工具执行质量，或证明代表整个生产 |
| 参数化合成流量 | 有意识让稀有状态发生，并检查指定计数器 | 用一条人工流量概括真实业务组合 |

## 三、路由热点：命中率好看，不代表整个池子跑得好

论文的跨副本测试中，llm-d 路由同时考虑前缀亲和与 token 负载。Terminal-Bench 2.1 会话开头有长共用前缀，最早缓存它的少数副本被反复选择，其他副本接近空闲。团队不是简单关掉亲和，而是把 token-load scorer 的上游从**估算 token 数**换成**真实分词计数**，从而纠正失衡。公开 WEKA 轨迹的前缀哈希按会话隔离，没有构造出相同的跨会话热点。论文没公布修复后吞吐提升的幅度。[§8 路由阶段](https://arxiv.org/html/2611.25905v1#S8)。

这值得在部署验收里做一个单独的 2×2：

- 一轴是**会话间共享真实长前缀**与**只在会话内复用**。能使用缓存命名空间时，优先保留原提示和分词，只改变共享域；如果只能加 marker，就核对 token 数与前缀截断位置。
- 一轴是**估算 token 负载**与**实际分词计数**。先固定亲和权重、到达序列和拓扑，再考虑重新调权。
- 每个副本记录排队 token、需重算的 prefill token、实际命中、排队时长和 p95 TTFT，同时看全池成功任务/s。不能用全池平均命中率掩盖少数副本的队列尾部；不同容量的副本还需按其承载能力解释偏斜。

这里要验证的是：**少搬一次 KV、少算一段 prefill 的局部收益，是否抵得过把下一批请求送进热点队列的代价。**

## 四、offload 写入有流量，为什么 24 次跑测仍没测到回读？

论文的覆盖测试运行于 **DeepSeek-V4.1-Flash-1017、8×H200、vLLM** 的单套配置，不能与 §8 四模型容量结果合并。此前 24 次跑测涵盖 smoke、真实运行、公开轨迹回放、全内容轨迹回放及合成负载；持续负载触发了 GPU→CPU 的路径，部分还让 CPU 层淘汰，但 CPU→GPU restore 的请求执行路径一次也未命中。[附录 D.1/D.2](https://arxiv.org/html/2611.25905v1#A4.SS2)。

回读至少需要两件事同时发生：前缀已从 GPU 层淘汰但仍在 CPU 层；同一前缀又在这个时间窗里被请求。GPU 撑满不保证出现第二步。如果重访过早，直接命中 GPU；如果太迟且 CPU 已淘汰，就可能重算，仍不是回读。

作者随后把 200 组各 65,536 token 的独立前缀组成约 1,311 万 token 的工作集，为日志中 GPU KV 池约 958 万 token 的 **1.37 倍**。以约 1 req/s 低于约 2.5 req/s 实测能力的节奏发起带重访的合成负载，CPU tier 为 512 GiB，未被该工作集占满。Table 12 从 Pod 重启后的零计数开始，记录到：

| 验收信号 | 报告结果 | 不能据此声称 |
| --- | ---: | --- |
| CPU→GPU 累计回读字节 | 108.1 GB | 固定可交付带宽 |
| CPU→GPU 操作次数 | 2,816 | 2,816 个成功用户会话 |
| CPU→GPU 累计操作时间 | 3.33 s | 整场回读墙钟时间或请求延迟 |
| GPU→CPU 累计写入字节 | 193.8 GB | 反向恢复成功 |
| 请求期代码执行 | `submit_load` 函数体命中；新增 124 条 offload/tiering 语句 | 输出正确、CUDA kernel 已覆盖或线上必定触发 |

不要直接用 108.1 GB 除以 3.33 s 当作端到端有效带宽；它缺少共同墙钟区间及并发语义。**1.37× 也是针对该配置构造的触发工作集，不是通用容量阈值或建议。** 更可靠的验收需要在同一请求上确认淘汰、慢层命中、完成回读、正确使用所还原 KV，并区分意外重算与预期回退；再用真实墙钟窗口报吞吐，用关键路径计时报延迟。

## 五、把这三件事放回同一套上线门禁

建议按环节选择分母，不要让一个 tokens/s 数字代替所有验收：

1. **模型服务器定容**：固定引擎、模型、并行拓扑、预热状态和采样参数，在目标模型轨迹上扫 offered session arrival rate。单独统计已接纳、完成、取消和失败任务，并给出明确的请求级 TTFT/TPOT 与会话级成功率/尾延迟门槛。若要隔离轨迹效应，优先用能处理两类输入的同一回放器。
2. **路由压力测试**：保留跨会话共享前缀的真实流量，再加相同到达时刻的隔离对照，观察副本排队与独立部署单元的有效负载。比较“满足 SLO 且成功”的任务数/秒，不仅比较引擎的 output tokens/s。
3. **缓存状态测试**：围绕实测有效 KV 池容量扫工作集和重访间隔，先验证单次正确回读，再加入同时重访的突发负载，观察 CPU→GPU 与主计算的争用。至少报告方向、请求关键路径、p99 restore stall、重算与回退；不要把 CPU 层数据直接当远端层表现。
4. **真实任务复验**：独立运行有明确完成判据的 agent 任务，校验回放所不能判断的分支决策和执行质量。线上直方图只能作为漂移预警，不能证明实验中的会话图或 prefix locality 已复现。

**先想好要证伪什么，再选负载。** 公开轨迹回答“这套栈能不能先调起来”，目标模型回放回答“这类业务能接多少”，定向合成回答“特定状态是否真的被触发”，真实运行回答“任务有没有做对”。把四个答案分开，才能知道需要加卡、改路由，还是先补一个根本没运行到的缓存路径。
