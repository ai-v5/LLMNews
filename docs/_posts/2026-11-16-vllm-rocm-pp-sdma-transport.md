## 先说结论：别让搬数据的人抢了算题人的位置

模型做流水线并行（PP），就是把不同层放到不同 GPU。前一张卡算完，必须把中间结果交给后一张卡，后者才能继续算。

看上去，这只是一次 GPU 间的数据拷贝。真正麻烦的是：**拷贝可能也占用计算单元，和正在执行的矩阵乘法争资源。** 带宽看起来不差，计算却被拖慢了。

vLLM 的 [PR #65658](https://github.com/vllm-project/vllm/pull/65658) 于北京时间 2026 年 11 月 15 日 15:56 合入，为 ROCm 的 gfx950 路径接入 SDMA 拷贝引擎，公开实验针对 MI355X。思路不是把模型算得更聪明，而是把跨卡搬运尽量交给专职硬件，让计算单元少受打扰。

但这次读代码，有一个比性能数字更值得提醒的发现：**PR 正文仍在介绍早期方案，最终合入实现已经换了结构。正文中的端到端提升不能直接贴到新实现上。** 本文以合入提交 `4244a09e` 为实现依据；实验数字单独说明来源与适用范围。资料复核截至北京时间 11 月 16 日 05:39，覆盖过去 24 小时公开合入的更新。本文没有在 MI355X 上复跑测试。

## 一、为什么“拷贝快”不等于“推理快”

在这里，要分开看三个问题：

1. 搬一块数据要多久？这是传输带宽问题。
2. 搬运同时，旁边的计算慢了多少？这是资源干扰问题。
3. 放进完整服务后，吞吐和首 token 延迟改善多少？这是系统收益问题。

同样的跨卡通信，可以由占用计算单元的内核完成，也可以使用独立拷贝引擎。前者不仅消耗互连与显存带宽，也可能争用本该执行模型计算的 CU。SDMA 的价值，就是减少这部分计算资源竞争。

PR 作者用一个很具体的微基准说明动机：在发送端执行大型 BF16 GEMM，同时持续向另一张卡复制约 201 MiB 的张量。正文报告，普通 peer copy 伴随的 GEMM 时间大幅增加，而显式 SDMA 路径对 GEMM 的影响很小。

这里最容易误读的是：“GEMM 慢了 5.1 倍”并不表示“整个模型能加速 5.1 倍”。它描述的是特定拷贝负载旁边的一项计算。真正推理还包含其他层、调度、等待和各种本地访存。

还有一个细节：微基准里的普通对照是 `torch` peer copy。不能仅凭这个表就声称对所有 NCCL/RCCL 版本与算法做过同样测量。完整服务里的 NCCL 对照，是另一组实验。

## 二、最终合入代码和 PR 正文，哪些地方不一样？

[评审意见](https://github.com/vllm-project/vllm/pull/65658#pullrequestreview-5866318805)已经明确指出这个问题：正文里的独立命令行开关、发送线程、共享内存计数器与旧测试文件，描述的是早期设计；端到端和 GSM8K 结果也来自那一版。

| 项目 | PR 正文的早期方案 | 最终合入代码 |
|---|---|---|
| 开启方式 | `--pp-sdma-handoff` | `VLLM_PP_TRANSPORT=copy_engine` |
| 传输组织 | 三个接收槽位、发送线程 | 复用统一的 `CopyEngineTransport` |
| 数据就绪与复用 | `/dev/shm` 计数器 | GPU 内存标记、流等待与 HSA 信号 |
| 输入输出保护 | 正文因此限制 eager、PP2 | 独立发送暂存区及接收暂存区，拷入持久输入张量 |
| 测试文件 | `test_pp_sdma.py` | `test_pp_transport.py` |

因此，不能把旧版的三槽位机制和新版的信号环拼成一个“完整架构”；也不能继续把旧开关写进部署指南。

ROCm 上默认 `auto` 仍走原有 NCCL 路径。新路径是明确选择加入，不是合入后所有请求都会自动使用。[模式选择代码](https://github.com/vllm-project/vllm/blob/4244a09e4d403d688c43dad19b895ec95ee2fa18/vllm/distributed/pp_transport/__init__.py)对此有直接分支。

## 三、从一块张量的旅程，看懂真正的设计

最终代码不是“直接把模型输出指针交给 SDMA 然后不管”。它在模型和跨卡传输之间，加了受控的暂存区。

可以把一步传输画成：

```text
发送端模型输出
  → 本地发送暂存区
  → SDMA 跨卡传输
  → 接收端共享接收区
  → 接收端持久输入张量
  → 接收端模型计算
```

多出来的两段本地拷贝并不免费。它们换来的是清楚的所有权：模型什么时候能改输出、通信什么时候能覆盖缓冲区，不再含糊。

### 第一关：发送区不能被下一步提前覆盖

发送端主流先等上一轮 `peer_done` 事件，再把新输出放入发送暂存区。打包结束后记录 `packed` 事件。

传输侧流等待 `packed`，这保证 SDMA 不会读到只写了一半的新数据。与此同时，下一轮打包也不能覆盖 SDMA 正在读取的旧数据。

这是发送端生命周期的核心：**数据生产完成，才允许搬；搬完之前，不允许把源缓冲区当空地。**

### 第二关：接收区是否空闲，必须由接收方回答

每轮有一个递增序号 N。发送侧流先等 `empty >= N-1`，确认上一轮接收区已经释放，才开始覆盖它。

接收端则等待 `full >= N`，确认本轮跨卡拷贝完成，随后把接收区内容复制到持久输入张量，最后写回 `empty = N`。

注意释放时机：新版不需要等接收端完成整段模型计算。**只要内容已经安全搬入独立的持久输入张量，共享接收区就可以让下一轮使用。** 这是与“模型直接读共享槽位”不同的生命周期设计。

接收等待和本地拷贝通过 `AsyncIntermediateTensors` 延后到真正读取 `.tensors` 时入队，因此此前的输入准备工作还有机会与传输重叠。这不是取消依赖，而是把等待放到实际需要数据的位置。[发送与接收实现](https://github.com/vllm-project/vllm/blob/4244a09e4d403d688c43dad19b895ec95ee2fa18/vllm/distributed/pp_transport/copy_engine.py)

### 第三关：不同运行时之间，怎么确认“真的搬完”？

SDMA 提交走 ROCr 的 HSA 接口，模型工作走 HIP/PyTorch 流。两个队列体系不能靠“CPU 已经调用过函数”来证明先后顺序。

[SDMA 实现](https://github.com/vllm-project/vllm/blob/4244a09e4d403d688c43dad19b895ec95ee2fa18/vllm/distributed/pp_transport/rocm_sdma.py)使用以下连接方式：

1. CPU 先把数据拷贝排入 SDMA 队列，但给它们挂一个尚未开放的依赖信号。
2. HIP 侧流完成打包等待、接收区空闲等待后，把依赖信号写成 0，放行传输。
3. 两个引擎的数据拷贝都完成后，再写两份 8 字节序号：远端的 `full` 和本地的 `sent`。
4. 侧流等待 `sent >= N`，随后记录的 `peer_done` 才能覆盖真实的数据搬运。

这样，“模型生产数据”和“SDMA 搬运数据”之间，“SDMA 完成”和“接收端读取”之间，都有可检查的依赖。

信号使用 16 项环形存储。重复使用一项之前，代码会等待它上次的 `sent` 拷贝完成，避免重置信号让仍在排队的操作失去条件。**16 是信号资源的轮换容量，不是 16 份模型激活缓冲区。**

## 四、为什么不直接调用一个 HIP 异步拷贝函数？

这正是硬件适配最容易被一行 API 掩盖的部分。

PR 正文针对 HIP 7.16 环境报告：某个“偏好 copy engine”的批量接口选项没有把设备间 peer copy 引到预期引擎；另一条 NoCU 路径甚至出现 API 返回成功、数据却没有完成拷贝的现象。

最终实现直接调用 `hsa_amd_memory_async_copy_on_engine`，显式选择引擎 2 和 4，把每个张量按 256 字节对齐的分块分到两个引擎，还先检查这些引擎对目标 GPU 是否可用。

这些是该硬件、软件版本与实现中的选择，不是对所有 AMD GPU 的通用建议。一个叫“异步”“NoCU”的接口，不足以证明它真的走了目标硬件路径。至少还要看数据正确性、引擎选择和对并发计算的影响。

此外，SDMA 不占用计算 CU，不等于传输完全免费。它仍然占用显存和互连资源；本地打包与复制也还在。这里改善的是资源竞争的形态，而不是让数据移动消失。

## 五、到底快多少？把证据分成三层

**第一层，代码事实。** 合入代码确实接入了 gfx950 的显式 SDMA 路径，并实现相应信号与流同步。这可直接从固定提交核对。

**第二层，作者早期实验。** PR 正文给出的微基准中，SDMA 带宽为 64.5 GB/s，普通 peer copy 为 59.3 GB/s；发送端并发 GEMM 的耗时增幅分别为 1.4% 和 411%。它主要支持“降低计算干扰”这个机制判断，而不是巨大带宽跃升。

同一正文报告，早期方案在 MiniMax-M3.1-Flash、TP1×PP2、eager、16K 输入、只生成 1 token 的负载中，四轮交替对照的请求吞吐平均增加 3.6%，平均 TTFT 减少 3.4%。这是偏长输入预填充的实验，不是长输出 decode 或所有服务负载的代表。

**第三层，最终实现的收益。** 评审明确要求在当前代码上重跑。本文核查的 PR 正文、公开评论和评审中，没有找到把同一组完整性能结果重新绑定到最终合入提交的补充记录。因此，本文不把 3.6% 写成最终版本已经验证的收益，也不把早期 GSM8K 小样本结果当作最终版本的完整正确性证明。

这不是否定优化，而是把“机制可信”“有早期正面数据”“最终版本已验证”三件事分开。

## 六、测试验证了什么，还缺什么？

最终[测试代码](https://github.com/vllm-project/vllm/blob/4244a09e4d403d688c43dad19b895ec95ee2fa18/tests/distributed/test_pp_transport.py)包含 PP2、PP4 链式传输，以及某一 rank 初始化失败时各 rank 是否作出一致选择的场景。

链式测试运行 40 步，交替改变行数，并故意让发送方或接收方变慢。最后一段检查张量形状与数值。这个设计不是只验证“正常情况下能拷过去”，而是专门逼出提前读、提前覆盖一类错误。

但“仓库里有这些测试”不等于“已经证明这些场景全部在 MI355X 上通过”。正文的四项通过记录指向旧测试文件；最终 diff 又把公共测试加入一项 NVIDIA L4 CI 配置。因此，不能拿它替代最终 MI355X 的实机结果。

从部署边界看，合入实现要求 TP=1、PCP=1、同一节点、相邻 PP 设备可做点对点访问；ROCm 路径要求 gfx950，并检查指定 SDMA 引擎可用。最终 transport 本身没有沿用旧正文中的 PP2 和 eager 限制，但这也不意味着任意 PP 深度、任意 CUDA graph 模式都已有完整性能和正确性验证。代码支持边界、测试覆盖边界、生产可用边界，需要分别确认。

## 七、这件事给推理系统设计的启示

我们的判断是：这项工作的价值，不在于又找到一个百分之几，而在于展示了怎样把“通信优化”拆成真正可落地的工程问题。

- **首先看干扰，不只看带宽。** 一条通信路径单独跑得很快，不代表和 GEMM 同时跑也划算。
- **同步协议和搬运 API 同样重要。** 不保护源缓冲区、不证明接收完成，再快的引擎也可能搬出错误答案。
- **有时多复制一次，反而更容易正确地重叠。** 暂存区增加本地开销，却让模型输入输出和通信生命周期脱钩。是否值得，最终仍要端到端测量。
- **评测必须跟着代码版本走。** 重构会改变缓冲、依赖和临界路径，旧实验不能自动继承。尤其在异步系统里，“逻辑一样”并不保证性能和时序行为一样。

一句话概括：**SDMA 负责搬运只是第一步；真正的系统优化，是让每一块数据在正确的时间被生产、搬走、消费和复用，并最终证明这些安排改善了服务。**
