## 先说结论：容量够，不等于下一次分配能成功

大模型训练的显存问题，通常从一张账单开始：参数多少，梯度多少，优化器多少，激活多少。加起来没超过显存容量，似乎就应该跑得动。

但这张账单漏掉了一个问题：**下一步计算要用的那块内存，现在能不能安全地交给它？**

我们可以把显存想成仓库。仓库还有空位，不代表某条流水线能立刻领到一块足够大、已经确认不再被其他流水线占用的场地。等待、回收和重新分配，本身也可能让训练停下来。

这不是要求把所有显存问题都归结为碎片。恰恰相反，真正重要的是分清：容量不足、单块大小不合适、跨流复用受限，以及对象本来就没有释放，是四类不同的问题。

本周以 Domyn 的 EUROPA 工程报告为入口，讨论这类容易被容量公式掩盖的瓶颈。依据是 **11 月 12 日公开报告、上游代码和官方文档**，不是我们自行复跑的性能结果。资料核对至北京时间 11 月 16 日 04:46，具体实验条件以下文限定为准。

## 一、案例到底证明了什么？先把数字分开

EUROPA 的实验模型约 **951.9B 总参数、32.8B 激活参数**。公开数字来自训练配置和性能试验，不代表完整预训练已结束或权重已发布。一个训练副本使用 384 张 GH200，节点内 EP=4；稠密参数分片跨 384 卡，专家参数对应的分片组跨 96 卡。[原始报告](https://www.domyn.com/blog/training-1t-moe-eu-public-infrastructure-pytorch)

最容易误读的是两组加速数字：

| 实验口径 | 可以说明什么 | 不能说明什么 |
|---|---|---|
| 累积优化从 90 到 1,293 tokens/s/GPU | 整体工程配置改善很大 | 不是一个开关带来约 14 倍加速；序列长度也由 8K 变为 64K，且采用 rank 0 第 4–10 步的中位数 |
| 三项显存生命周期/分配调整后，996 到 1,210 tokens/s/GPU | 该配置下，显存管理已经影响训练速度 | 不能把约 21% 全归给单独的上游 API |

后一组实验的峰值 reserved 显存从 88.1 降至 74.6 GiB，发生 allocator retry 的 rank 从 384 个降至零。诊断快照中，侧流保留 27.3 GiB，其中只有 6.4 GiB 在用，其余 20.9 GiB 无法直接供计算流复用。计算流自己的缓存约有 4.5 GiB 空闲，却找不到能容纳 4 GiB SonicMoE 工作区的单块。三项调整分别是：缩短归约后梯度的生命周期（逐层梯度范数 hook 曾让梯度额外存活，占约 9 GiB）；在计算流上准备 all-gather 缓冲区，用异步通信句柄维护完成依赖；把 BF16 all-to-all 的梯度接收缓冲区也分配到计算流。[报告的显存分析与实验](https://www.domyn.com/blog/training-1t-moe-eu-public-infrastructure-pytorch)

**我们的判断：最有价值的不是“省了多少 GB”，而是给出了“哪类空闲内存不能服务谁”的解释。** 这是一个可被验证、也能被证伪的因果假设，比看到 OOM 就减小 batch 更进一步。

## 二、为什么 FSDP 特别容易遇到这个问题？

FSDP 的核心做法是分片保存参数，需要计算某层时再把它们收集起来，计算结束后按策略重新分片。它是在显存占用和通信之间做交换。

如果每层都按“先收完参数，再算这一层”的顺序执行，通信等待会很明显。于是系统提前收集下一层的参数，希望在当前层计算时把通信做掉。

概念上可以画成：

```text
计算：       [第 i 层计算]             [第 i+1 层计算]
通信：          [提前收集 i+1 参数]
内存：       当前层参数 + 下一层收集缓冲 + 激活 + 工作区
```

这带来两个代价。

**第一个是存活时间。** 下一层参数提前准备，就得提前占据空间；预取越深，同时在场的数据往往越多。吞吐量优化和显存优化不是两条互不相干的线。

**第二个是安全复用。** CPU 已经不再持有一个张量，不等于 GPU 上此前提交的异步操作已经结束。如果另一条流立刻重用它的地址，可能发生覆盖尚未完成的数据读取。因此运行时要跟踪依赖，不能只看 Python 对象是否消失。

PyTorch 官方文档区分 `memory_allocated()` 与 `memory_reserved()`：前者观察张量占用，后者观察缓存分配器管理的总内存；并要求跨流使用时正确建立同步和生命周期关系。`record_stream()` 与显式等待处理的是不同侧面的安全性，不能为了降低显存数字随意删掉。[CUDA 内存与流语义](https://docs.pytorch.org/docs/2.15/notes/cuda.html)

这解释了一个反直觉现象：**把计算变得更异步，可能降低等待，也可能制造更多暂时无法复用的内存。** 优化目标应该是每一步更快地安全完成，而不是时间线上彩色条块重叠得越多越好。

## 三、把 all-gather 放到计算流，是不是又退回串行？

这里容易被接口名字误导。需要分开看两件事：

1. 谁发起操作、分配和准备缓冲区；
2. 网络传输实际如何异步执行，什么时候等待结果。

当前 PyTorch 主线的公开接口叫 `set_unshard_in_current_stream`。其说明明确了交换条件：收集参数前的 copy-in 和类型转换会在当前流执行，不能再与当前流计算并行；但提前发出的异步收集，仍可以与后续计算重叠。前向需要显式预取，或者提前调用异步 `unshard`，否则每层收集都可能暴露在关键路径上。默认值为 `False`。[已落地主线代码](https://github.com/pytorch/pytorch/blob/a63f799279ba419ce1920356e91e0701cb51f40a/torch/distributed/fsdp/_fully_shard/_fully_shard.py)

可以用下面这张账单理解，而不是简单判断“串行好”还是“并行好”：

```text
净收益
≈ 减少的回收/同步等待
 + 更好复用带来的容量余量
 - 挪到计算流上的准备开销
 - 预取不足后暴露出的通信等待
```

这是分析框架，不是拟合出来的性能公式。它告诉我们应当分别测什么。

如果原来没有发生分配重试，回收等待那一项可能接近零。此时改接口可能只剩额外准备开销。因此“某个 1T 作业快了”不能推出“所有模型都应当默认开启”。

## 四、公开代码已经有什么？还有什么不能直接照抄？

TorchTitan [PR #5627](https://github.com/pytorch/torchtitan/pull/5627) 已于 11 月 8 日合入。它的小模型实验报告：峰值 reserved 内存约降 10.6%，吞吐却约降 0.7%。这恰好是前面交换关系的具体例子：**显存省了，速度不一定立刻上升。**

PyTorch 对应接口在提交 [`a63f799`](https://github.com/pytorch/pytorch/commit/a63f799279ba419ce1920356e91e0701cb51f40a) 中进入主线。这里要区分“主线能看到实现”和“你当前安装的稳定发行版已经支持”。本文不据此宣称所有稳定版本都能直接使用，也不建议依赖旧的私有接口名称。

上游讨论还特别关注预取链：普通顺序 decoder、重复调用的模块、MTP 和多模态路径，不能默认共享同一套执行顺序。只有预取链覆盖了真实调用路径，提前收集才真正提前。[上游讨论](https://github.com/pytorch/torchtitan/pull/5627)

因此，迁移时先确认三个条件：

- **版本条件：**本地实际代码包含哪个接口，行为和文档是否一致；
- **执行条件：**模块是否按预期调用，是否有重复执行、分支或重计算；
- **收益条件：**当前瓶颈真的是跨流复用和重试，而不是算子本身或网络拥塞。

不能跳过前两项，直接用第三项的吞吐数字证明正确性。

## 五、对训练系统建模的启示：不能只留一个“显存总量”字段

下面是我们的工程分析，不是原报告给出的新测试结果。

如果仿真器只计算 `参数 + 梯度 + 优化器 + 激活 < HBM`，它最多能判断静态容量是否大致可行。对于异步通信，它还需要表达时间。

### 1. 给缓冲区加上生命周期

每一类大缓冲区至少应有：大小、分配时刻、最后消费者、可安全复用时刻。特别是 all-gather 输入/输出、梯度通信接收区、反量化区和算子工作区。

这里的“最后消费者”不是最后一个 Python 函数，而是最后一个确实访问该地址的设备操作。若事件依赖没有满足，即使逻辑上已经释放，也不能当成立即可用容量。

### 2. 区分占用和可复用域

两个缓冲区不同时存活，也未必能无代价复用。需要说明它们属于哪个分配器、流或专用内存池，以及跨域复用需要什么同步。

一个更有用的输出不是“剩余 20 GB”，而是：

> 下一次需要 4 GiB 工作区；它所在的分配路径现在能提供多大的连续块？若不能，回收会等到什么时候？

这并不意味着每个早期容量模型都要实现完整分配器。可以先把“静态可行”和“生命周期验证通过”分为两级，不把前者包装成后者。

### 3. 把通信和内存策略一起搜索

更深预取、保持参数不重分片、通信量化、激活卸载，都可能增加一种临时缓冲并减少另一种等待。分别挑选每个局部最优，再拼在一起，可能得到全局最差的峰值。

合理的实验单位应该是完整策略组合，但解释结果时仍需拆分消融。否则看见总吞吐上涨，不知道下一次换网络或序列长度后，该保留哪部分。

## 六、从 384 卡扩到更多卡，还要问什么？

报告另列了复制训练副本的结果：相对于单副本，双副本的单卡吞吐保留 99.3%，四副本保留 89.4%；批量同步增大。这不能当成固定全局 batch 的强扩展结果。四副本对应约 **3.58 倍总吞吐**，是 `4 × 89.4%` 的计算，并非四倍线性扩展。[规模实验](https://www.domyn.com/blog/training-1t-moe-eu-public-infrastructure-pytorch)

对实际训练计划，更应该继续问：

- 更大全局 batch 能否保持目标收敛效果？如果需要更多 token 才达到相同质量，总吞吐增益会被抵消多少？
- 多副本梯度同步与现有通信同时运行时，尾部 rank 会不会放大每一步等待？
- 数据分布和长文比例变化后，工作区峰值是否还在当前预留范围内？
- 检查点、故障恢复和共享集群扰动是否计入有效训练时间？

短窗口 benchmark 可以验证一个优化方向，但不能独自回答“这次预训练几个月能训完”。后者需要长时间、跨 rank 的有效吞吐和停机记录。

## 七、值得直接带走的排查顺序

遇到“显存没满，训练却频繁卡顿”，可以按下面顺序缩小范围：

1. **固定实验口径。** 保持模型、序列长度、数据次序和并行配置不变。记录预热段，避免只看启动后的几个快步骤。
2. **同时看内存和时间线。** 分开记录 allocated、reserved、分配重试，以及通信等待。重试次数下降但 step 没变，说明还没触到主瓶颈。
3. **找到最大申请者。** 记录它申请时需要的单块大小，不只统计总空闲量。
4. **检查释放依赖。** 找到最后使用缓冲区的通信或 hook，确认安全释放时点。不要用删同步来“优化”。
5. **分别调整和组合验证。** 缩短对象存活、改变分配流、调整预取深度分别测试，再测组合。记录负收益结果。
6. **验证正确性与长时间稳定性。** 检查 loss、梯度和不同随机种子下的行为；把短时数值一致与完整训练质量分开报告。

最后再强调一次：本文不是“打开一个开关就能把训练提速”的指南。

**真正可迁移的经验是：显存不只是容量，还是带有时序和所有权的资源。** 当 FSDP、通信量化、卸载与算子工作区叠在一起，谁分配、谁最后使用、什么时候能复用，已经和通信带宽一样，是训练系统的一等设计问题。
